# FastSql 与 SqlSugar 对照

> 这份文档只做一件事：把 FastSql 与 SqlSugar 放在**同一台真库、同一副表、同一批活**上比，并且把每个结论钉到可核的出处上。
>
> 设计论证在 `docs/fastsql-orm-design.md`（规格），日常用法在 `docs/fastsql-orm-usage.md`（用法）。本文不是第三份设计文档，也不改那两份的口径。

## 1. 量具与重跑法

量具是一次性控制台工程，放在 **`sql/obj/sqlsugar-compare/`**（`obj/` 被 `sql/.gitignore` 挡住，不进版本库）：

- `Program.cs`：**十七段对照活**（1–10 十段，另加 `3b`…`3g` 六段与 `10b` 一段 ∶ 批量、逐条、宽表、`UseParameter`、颗数因果、每语句行数扫、裸 ADO 对照、**每趟换一批全新值的同一形状**、**计划缓存那一侧的直接读数（DMV）**、分页首页与第二页、读物化、留痕次数、引号、地板、**留痕存活探针**、**事务内装载与约束二选一**）；
- `fscompare.csproj`：`SqlSugarCoreNoDrive` 5.1.4.218 + `Microsoft.Data.SqlClient` 7.1.0 + `ProjectReference` 到工作树的 FastSql 三颗程序集，并挂 `FastSql.Generators` 为 Analyzer（否则消费者程序集里没有 G2 注册表，`FastSqlOrm.Create` 会报"DbKind.SqlServer 未在 ProviderRegistry 中登记"）；
- `run.txt`：最近一次跑出来的原始输出；`run-A.txt` / `run-B.txt`：**本轮同一份二进制连跑两趟的原始输出**（两趟各带一个字母标签，见下）。

**标签是本轮加的一条纪律**：`fscompare.exe d` / `fscompare.exe e` 这样传一颗字母参数，§2.14 那六族裸 ADO 的表名就跟着变成 `cmp_p1d`…`cmp_p8d`。原因是计划缓存的**键是语句本文**：上一趟与这一趟的表名相同时，本文也相同，于是 `计划 +N 颗` 整列读成 `+0`（第一版就是这么红的），一个字的标签把两趟隔开。

**读数的出处怎么算（六趟，两份原始文件 + 一份旧文档）**：本节表格里写"六趟"的区间，下界与上界各自由两副读数钉住 ∶ 本轮的 `run-A.txt`/`run-B.txt`（在工作树里，可直接开），以及上一版文档（提交 `2415164` → `d22ac08`）里那四趟留下的区间。更早那四趟的原始输出**不在版本库里**（`sql/obj/` 被 gitignore 挡住），本轮重跑时已被覆盖，所以它们的读数只以区间形式存在于 `git show d22ac08:sql/docs/fastsql-vs-sqlsugar.md` 的表格里——这是一条**降级了的可核性**，本文照实写在这里。本轮新增的格子（§2.14 计划缓存）只有两趟，格子里明写"本轮两趟"；上一轮只有两趟的三格（§2.6 换数据、§2.12 事务、§2.13 留痕存活）本轮补到四趟，格子里的标注已跟着改。个别形状在量具里出现在两节（`UseParameter` 的 2000×6 在 `3b` 与 `3d` 各跑一次），那种格子本文写出实际趟数（最宽的一格八趟）。

重跑（已验：从该目录 `dotnet build` 成功）：

```powershell
cd E:\Resource\Fast\sql\obj\sqlsugar-compare
dotnet build -v q --nologo          # 0 警告 0 错误
$env:FASTSQL_DRIVERS_CONFIG = "E:\Resource\Fast\sql\FastSqlDrivers.json"
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()   # 不清这行，控制台见证会是 GBK
bin\Debug\net10.0\fscompare.exe d | Out-Null; Copy-Item run.txt run-A.txt   # 标签 d
bin\Debug\net10.0\fscompare.exe e | Out-Null; Copy-Item run.txt run-B.txt   # 标签 e：两趟的表名不同名，§2.14 的计数才作数
```

连接串的取法和集成层判据同一条：`FASTSQL_TEST_CONNECTION` 优先，其次 `sql/fastsql-test.connection.local.txt`（本地文件，gitignored）。量具全程不打印口令。

**段序是硬的**：`9`（留痕存活探针）与 `10`/`10b`（事务×装载）必须排在所有量墙钟的格子之后。这不是排版偏好——本轮第一版把事务那几段放在中间，跑出来的 `run.txt` 里**后面每一格对面的留痕全成了空白**（`OnLogExecuting 响 0 次`、`(无文本)`），因为事务内装载抛异常会把 `Ado.IsEnableLogEvent` 按灭且不恢复（§2.13 就是这一笔翻出来的证据）。这次翻车留着，因为它同时是结论和排雷图。

**计时纪律**（五处容易做假的地方，都堵上了）：

1. 每格取**三趟最小值**；
2. 计时段**只包住活本身**，`TRUNCATE`、建连接、建表都在计时段外——这条不是洁癖：早前一版把 `TRUNCATE` 算进去了，量出 FastSql L1 207 ms 对 SqlSugar 38 ms 的 5 倍差距，重排之后两家在同档（六趟区间 30.66–123.55 对 28.97–96.03，下界差 1.7 ms，§2.1）；
3. 表里的"句"指**一次命令文本**（一次 `ExecuteNonQuery`）。SqlSugar 的分块会把多段 `INSERT` 用 `;` 串进同一颗命令文本里，所以"1 句"**不等于**"1 条 INSERT"，本文在下面会写清到底几段。
4. **本节绝大多数毫秒数是六趟完整跑的区间**（来历见上上段），不是单趟。这一条也是被数据教的：同一格跨趟能从 38 ms 跳到 537 ms（§2.1 的 SqlSugar 内联那一档），本轮又添一副 33.75 跳到 123.55（§2.1 的**本家** L1 那一档），单趟报出来的任何一位小数都会假装精度比实际有的高。区间下界用于排名次，上界用于说"抖多大"；**两副区间重叠的格子，本文不再排名次**（据此收回的名次累计三处：§2.8 那句"对面稳定快约 10%"、§2.5 中间两档的排序、§2.1 那句"长尾只出现在 SqlSugar 那两档"——第三处是本轮翻的，见 §5.8；新增的格子从一开始就按这条办——§2.2 的配对一比一、§2.12 的墙钟、§2.14 的每族墙钟都不报名次）。
5. **§2.12 那一档的形制与别处不同**：它把 `begin → 写 → rollback` 整段计时，而别处只计"写"，所以那一档只跟同形制的那一档比，不拿来跟 §2.1 论高低。

## 2. 实测：十四格原始读数

### 2.1 批量插入 2000 行 × 7 列

| 走法 | 墙钟（六趟） | 留痕读数 |
| --- | --- | --- |
| FastSql L1 装载通道 | **30.66 – 123.55 ms** | `CopyChannel ∶ 2000 行 ∶ 1 次递交 ∶ 库里 2000` |
| FastSql L3 多值语句 | 1176.07 – 1617.09 ms | `MultiValue ∶ 7 块 ∶ 每块 315 行 ∶ 语句 7 句 ∶ 参数 12000 颗 ∶ SQL 文本累计 93263 字` |
| SqlSugar `Fastest<T>().BulkCopy` | **28.97 – 96.03 ms** | `OnLogExecuting 响 1 次 ∶ 参数 0 颗 ∶ SQL 文本累计 79 字 ∶ INSERT 0 段` |
| SqlSugar `Insertable(list)` | 38.19 – **537.38 ms** | `OnLogExecuting 响 1 次 ∶ 参数 0 颗 ∶ SQL 文本累计 328580 字 ∶ INSERT 10 段` |
| 裸 `SqlBulkCopy`（地板，§2.11） | 19.91 – 31.25 ms（只算复制） | 库里 2000 |

（"每句 315 行 × 2000 行"这一副 FastSql 的活在量具里出现在两处（本节的 `1` 与 `3d`），每处各六趟，合起来十二副读数，跨度 1 176.07 – 1 617.09 ms（比 38%）。两处各写自己那六趟的区间，不混成一副。）

SqlSugar 批量那一档写出去的形状（原文截断）：

```sql
INSERT [cmp_sugar]  ([CustomerName],[CustomerId],[Amount],[State],[CreatedAt],[Note])
   SELECT N'客户1' AS [CustomerName],N'7' AS [CustomerId],1.25 AS [Amount],N'1' AS [State],'2026-10-05 01:02:03.000' AS [CreatedAt],N'cmp' AS [Note]
   UNION ALL
   SELECT N'客户2' ...
```

五个读数要合起来读：

- **装载通道这一档两边打平，而且这一格六趟区间整个重叠**：FastSql 30.66–123.55，SqlSugar 28.97–96.03，下界差 1.7 ms；上界这一轮反过来是本家更高（123.55 那一趟就是下面那条长尾）。地板（§2.11）在 19.91–27.54，所以两家各自都有约 **9–11 ms** 的"把自己那层套上去"的开销（下界相减），这一层两家同量级。
- **这一格第一次给到了"段数"而不是只有"句数"**：留痕里那句 `INSERT 10 段` 是在 `OnLogExecuting` 里数 `INSERT ` 关键字的颗数量出来的（先前版本此处写"按 `SqlServerInsertBuilder.cs:34-42` 推得 10 段"，那一档现在坐实了：2000 行 ÷ 每段 200 行 = 10 段，与推算逐字相同；本轮两趟仍是 10 段）。
- **SqlSugar 的批量默认根本没走参数**：参数 0 颗、文本 32.8 万字，值全部内联成字面量，**一次往返**送出去。这条读数直接打折一句旧说法，见 §5.1；而它的**红利条件**是上一轮量出来的，见 §2.6。
- **长尾这一笔不认家**：先前在这一格写下的是"**长尾只出现在 SqlSugar 那两档**"，本轮被本家自己的一趟否掉了——FastSql L1 本轮两趟是 **123.55 与 33.75**（3.7 倍），把它并进上一版四趟的 30.66–36.81 就是 30.66–123.55。同一份二进制、同一副表、同样是三趟取最小，本家这一档一趟能涨到三倍多。对面那两档照旧（`Insertable(list)` 上一轮四趟 53.48 / 537.38 / 38.19 / 43.57，本轮两趟 44.46 / 38.51；`Fastest.BulkCopy` 31.50 / 96.03 / 28.97 / 44.75，本轮 35.80 / 39.12）。跨度于是变成：本家 L1 **4.0 倍**、L3 1.37 倍，对面装载 3.3 倍、内联 14 倍——**"本家比对面稳一个量级"那句也跟着作废**，只剩"对面内联那一档跨度最大"还站着。本文**没有解释任何一副长尾**，只把量程报出来，并把名次钉在"下界"上（见 §6 第一条、§5.8）。
- **文本量是另一笔账**：同一批活 SqlSugar 写出 328,580 字，FastSql L3 写出 93,263 字加 12,000 颗参数。内联换到的是"不付参数的钱"（§2.5 量到了这一笔有多大），付出的是"服务端要为 33 万字的语句本文做编译"——这一笔先前只挂在"没量"那一栏，上一轮量了（结果是它会改名次，见 §2.6），本轮又把它换成**服务端侧的直接读数**（§2.14：那 33 万字里每一句都留下一颗计划）。

### 2.3 宽表 30 列 × 500 行

| 走法 | 墙钟（六趟） | 读数 |
| --- | --- | --- |
| FastSql `Auto`（不调 `WithBulk`） | **27.24 – 47.15 ms** | `Auto→CopyChannel` ∶ 1 次往返 ∶ 库里 500 ∶ `Reason` 原文是"500 行走 SqlServer 的装载通道（§12.1 的 L1）：不发 SQL 文本、不走参数，一次递交。通道内部怎么分批是驱动的事，对上层是一次递交一块；改写类钩子（`CudBuilding` / `ParameterBinding`）在这一档不适用" |
| FastSql L1 装载通道 | **30.84 – 39.12 ms** | `CopyChannel ∶ 500 行 ∶ 1 次递交 ∶ 库里 500` |
| FastSql L3 多值 | 1544.04 – 1949.06 ms | 8 块 ∶ 每块 65 行 ∶ 每块参数 1885 颗 ∶ 库里 500 |
| SqlSugar `Fastest.BulkCopy` | **30.51 – 35.99 ms** | 响 1 次 ∶ 参数 0 颗 ∶ 文本 83 字 ∶ INSERT 0 段 ∶ 库里 500 |
| SqlSugar `Insertable(list)` | 36.44 – **150.85 ms** | 1 句（内含 **5 段** INSERT，数出来的）∶ 每段 100 行 ∶ 参数 0 颗 ∶ 文本累计 242,442 字 |

**先前版本在这一格写下"全篇差距最大：24.8 倍"，同一格重跑三轮之后的结论是那句写歪了。** 三处要改：

- **同档对同档，宽表上两家都是装载通道，六趟区间整个重叠**：FastSql 30.84–39.12 对 SqlSugar 30.51–35.99，下界差 0.3 ms。**宽表不让 FastSql 的 L1 掉速**（§2.1 那格 2000 行 × 7 列它是 30.66–123.55 ms，行数差四倍而墙钟下界同档；本轮那副 123.55 是跨趟长尾，不记在形状的账上，见下面那条）——这一条先前只留在"见 §2.1，本文未在宽表上重跑"那一格里，现在补上了，而且两轮都补上了。
- **24.8 倍比的不是同一件事。** 那一趟是"FastSql 被点名只许走 L3"对"SqlSugar 走它的默认（内联）"。把 `Auto` 那一行放进来（27–47 ms），FastSql 面对同一副宽表的默认行为根本不付这笔钱。
- **L3 慢的真正原因不在"宽表"，在"每命令参数颗数"**，与表宽窄无关——§2.5 用一趟扫把这条钉死了。顺带把先前一条**推算**升成实测：`1 句内含 5 段` 是在 `OnLogExecuting` 里数 `INSERT ` 关键字数出来的，不再按 `SqlServerInsertBuilder.cs:34-42` 推（30 列 ⇒ 列数 >20 ⇒ 每段 100 行 ⇒ 5 段，算与数逐字一致，上一轮两趟与本轮两趟都是 5 段）。

（SqlSugar 内联那一档六趟的读数是 37.87 / 38.28 / 38.79 / 39.59 / 36.44 / **150.85**，另有一副不在本轮计时纪律内的早期读数 76.56——下界落到 36.44，上界从 77 ms 抬到 **151 ms**，所以本文把这格改按 **36–151 ms** 看待，名次仍钉在下界。上一版那句"除最早那一趟之外都在 38–40 ms"**作废**：150.85 是本轮两趟之一（另一趟给它的是 36.44），不是历史遗留。这一档现在与 §2.1 那条"长尾不认家"读成同一件事，见 §5.8。）

### 2.4 SqlSugar 的参数化那一条口：`UseParameter()`

先前版本的 §3.1 与 §5.1 说"对面也有参数上限意识，只是默认路径用不上"——那句**只有源码没有数**。上一轮把它跑了，本轮又跑了两遍（`UseParameter` 的窄表那副活在量具里出现在 `3b` 与 `3d` 两处，两处各四趟，再加上更早的两趟一共八趟；宽表那副只在 `3b` 一处，六趟）：

| 走法 | 墙钟 | 读数 |
| --- | --- | --- |

写出去的是真参数化多值，参数名每句重新编号（原文截断）：

```sql

VALUES(@CustomerName0,@CustomerId1,@Amount2,@State3,@CreatedAt4,@Note5),  (@CustomerName6,@CustomerId7, ...)
```

源码那一档与实测逐字对上（`ParameterInsertable.cs:111,129-132,171-187`）：起点是**写死的 100 行**，然后按 `pageSize * count > 2100` 连压 50⇒20⇒10，而那颗 `count` 是**实体列数（含自增列）**——所以 6 列实体（含 `Id` 共 7 列）是 7×100=700 ≤ 2100、不压，量到每句 100 行；宽表（含 `Id` 共 30 列）30×100=3000 > 2100、压到 50，实发每行 29 颗 ⇒ 1450。**每一句都压在 2100 以下：这一点先前只读到判据、没量到落地，现在量到了。**

但它与 FastSql 的分别也一并清楚了：**2100 对它是一道墙，不是一个目标**。100 行 × 21 列 = 2100 刚好不压，22 列才压到 50 行——它从不问"这一句多少行花多少钱"，只问"撞不撞墙"。而 FastSql 的 §12.3 公式问的也只是预算（`ParameterBudget * 9 / 10 / cols`），所以两家在这件事上是**同一种问法**，只是默认答案不同：2100 的九成 ⇒ 贴着曲线贵的那一端，100 行 ⇒ 贴着便宜的那一端。谁都没把"每命令颗数的超线性代价"放进目标函数（§2.5、§5.4）。

### 2.6 同一批形状，每趟换一批全新值：把"计划能不能复用"这一笔摘出来

**这一节是上一轮新开的，它改写了 §2.5 第 2 条的成立条件；本轮把它的趟数补到四趟，并把"机制那一栏"从空白换成直接读数（§2.14）。** 前面所有格子都跑在同一批数据上：三趟计时用同一副值，于是内联那一档每趟写出去的是**逐字相同的一大坨本文**——服务端第一次编译过之后，后面两趟复用的是什么，本文先前没有区分过。量具的做法是把值整体平移（每趟 `shift += 1000`，`Cell` 的 prep 里递增 ⇒ 三趟是三批互不相交的数据），形状、行数、颗数一颗都不动，只让"值"变。参数化那一族的**客户端**语句本文因此照旧逐字相同（服务端可见的那一份是否逐字相同，本轮才有答案，见 §5.7），而内联那一族的本文每趟都是新的（长度只差千分之几）。下表是四趟（上一轮两趟 + 本轮两趟）：

口径要钉死的一处：上一轮这一节**没有**直接读服务端的计划缓存（没查 `sys.dm_exec_cached_plans`，也没抓 TDS），"编译 vs 复用"是从"只有内联那一族变动"这一条对照推出来的——那时候本文把它写成**与源码形状一致的读数**，不是机制的证明。本轮 §2.14 把计划那一侧数到了，这一节因此升成"有机制读数为证的后果读数"；**仍未抓 TDS**，而"命中"与"重新编译"之间的服务端动作本文还是看不见（§6）。还有两点没试：只试了"每趟全换"，没试"每两趟换一次"这种中间档；每趟全换也让索引/page 分配的状态变了，本文无法把这一笔从编译那一笔里剥干净。

### 2.7 分页（表上 200 行，取 20 行；首页与第二页各一档）

| 走法 | 语句数 | 读数 |
| --- | --- | --- |
| FastSql `ToPagedAsync(1,20)`（`Auto`） | **1** | Items 20 ∶ Total **null** ∶ HasNext True |
| FastSql `ToPagedAsync(CountStar)` | 2 | Total 200 |
| SqlSugar `ToPageList(1,20,ref total)` | **2** | Items 20 ∶ Total 200 |
| SqlSugar `ToPageList(1,20)` 不要总数 | 1 | Items 20 |
| **FastSql `ToPagedAsync(2,20)`（`Auto`）** | **2** | Items 20 ∶ Total 200 ∶ HasNext True ∶ 写出去的两句在下面 |
| **SqlSugar `ToPageList(2,20,ref total)`** | 2 | Items 20 ∶ Total 200 |
| **SqlSugar `ToPageList(2,20)` 不要总数** | 1 | Items 20 ∶ 那一句是窗口函数外壳 |

这一格量的不是快慢而是**默认替你做什么**。FastSql 默认那一档在**首页**只发一条语句（`QueryEngine.cs:1225` 的 `size + 1`，多取一行探 `HasNext`），代价是 `Total` 为空；到**第二页起 `Auto` 自己换成 `CountStar`**（`QueryEngine.cs:1264-1271` 的 `Resolve`：`page == 1 ? SkipTotal : CountStar`），也就是两条——**这条换档上一轮只报源码、上一版实测到了，本轮再跑两趟还是同一形状**：第二页确实发两句，`Total` 也从 null 变成 200。要总数必须显式换 `CountMethod`（`src/FastSql.Abstractions/Query/IQuery.cs:19` 的 `PagedOptions` 默认 `CountMethod.Auto`）；`CountOverWindow`（单往返带总数）与 `SeparateTransaction`（同连接同事务两条）**今天直接抛异常**，不是静默降级。SqlSugar 的 `ref total` 是"要总数就固定两条语句"——`QueryableExecuteSql.cs:509` 那一档写得很白：先 `this.Clone().Count()` 再 `this.Clone().ToDataTablePage(...)`，两次往返、两次 `Clone()`。两边各有对面拿不到的东西：SqlSugar 拿不到"不写 `ref total` 之外还能选单往返带总数"，FastSql 拿不到默认给的准确总数。

四趟抓到两家第二页写出去的东西（每一趟的文本逐字相同），形状差得比想象中远：

```sql
-- FastSql ∶ ToPagedAsync(2,20) 的两条语句
SELECT [t0].[Id], [t0].[CustomerName], … , [t0].[Note] FROM [cmp_fast] AS [t0]
  ORDER BY (SELECT NULL) OFFSET @p0 ROWS FETCH NEXT @p1 ROWS ONLY
SELECT COUNT(*) FROM [cmp_fast] AS [t0]

-- SqlSugar ∶ ToPageList(2,20) 不要总数的那一条
SELECT * FROM (SELECT [Id],[CustomerName],…,[Note],ROW_NUMBER() OVER( ORDER BY GetDate() ) AS RowIndex
               FROM [cmp_sugar] ) T WHERE RowIndex BETWEEN 21 AND 40
```

三读数合起来：

- **本家在 T-SQL 上从不发 `TOP`，先前本文那句写错了**：第二页真发的是 `OFFSET…FETCH`（`SqlServerDialect.cs:39-53` 的 `EmitPaging`，缺省偏移落成常量 `0` 而不是省略子句），而首页那一档**同形**——本家没有 TOP 发射器（`SqlServerDialect.cs` 全文搜不到 `TOP`，方言册既有金标 `tests/FastSql.Tests.Dialects/SqlServerPagingTests.cs:49` 钉的就是 `OFFSET 0 ROWS FETCH NEXT @p0 ROWS ONLY`）。先前版本在 §2.6 与 §3.4 两处写下的"单条 `TOP n+1`"是本文读源码读歪的，上一轮翻掉，见 §5.6。首页那一句的**原文**当时没抓到（`fastSamples` 在第二页之前清空了），本轮仍然没抓到，所以这一句的根据是方言册 + 第二页的实测文本，不是首页的见证。
- **没有 `ORDER BY` 时两家都补了一颗，补的是两种东西**：本家补 `ORDER BY (SELECT NULL)`（`DialectBase.cs:461-470`，`PagingRequiresOrdering` 在 `SqlServerDialect.cs:31` 为 true ⇒ 语法要求它在，策略是"不替你排序，只让句子合法"）；对面补 `ORDER BY GetDate()`（`SqlServerQueryBuilder.cs:60` 写死）——那是**每行都不同的表达式**，等于替调用方造了一个不稳定的序。两者都不保证翻页不漏不重，但本家的写法不额外引入跨行变化，对面的会（本文仍未实测并发写下的漏重，见 §6）。
- **计数那句也不同形**：本家是 `SELECT COUNT(*)`，对面是 `SELECT COUNT(1)`（`QueryBuilder.cs:634-641` 的模板，化简成直查表；四趟里那一句原样，一个字节没变）。这一笔只是形状，没有代价差可量。

SqlSugar 不计数那一档也是单条。**首页这一格持平；第二页起两家都是两条，也持平——但两家在第二页上的"合法化排序"不是同一颗，这一格从"持平"变成了"持平且各注不同的东西"。**

### 2.8 读 200 行 × 7 列并物化

FastSql `ToListAsync` **1.37 – 1.73 ms** ∶ SqlSugar `ToList` **1.23 – 1.59 ms**（六趟）。这一格的口被连着改过两次：最早写"对面稳定快约 0.15 ms（10%）"，上一轮的四趟把那句作废（区间重叠 ⇒ 按 §1 第 4 条不排名次）。本轮两趟把两边的下界一起往下推了一档（1.41 / 1.37 与 1.23 / 1.30），于是配对读数变成四副：**上一轮两副是 1.54 对 1.36、1.62 对 1.59，本轮两副是 1.41 对 1.23、1.37 对 1.30——四副全朝同一个方向（对面快 1.9%–12.8%）**。这比"下界略快"更有内容，但按 §1 第 4 条它仍然进不了名次档：**两副区间在 1.37–1.59 整个重叠**，而本格六趟跨度是本家 26%、对面 22%，比那四副配对的差还大。所以这一格现在的口径是：**同一量级、方向一致朝对面、幅度小于本格的抖动**——"稳定快 10%"那句不许写回来，"完全持平"那句也不许写（四副配对没有一副是本家胜）。

| SqlSugar `Insertable(list)` 500 行 | `OnLogExecuting` 响 **1 次**（内含多段 INSERT） |
| SqlSugar `Fastest.BulkCopy` 500 行 | `OnLogExecuting` 响 1 次，文本是 `Begin BulkCopy name:[cmp_sugar] ,count: 500,current time: …` |

SqlSugar 那条"伪 SQL"是设计如此，不是日志坏了：`FastestProvider.cs:548` 在装载前发一句 `Begin {title} name:… ,count: N` 给 `OnLogExecuting`，紧接着 `:545` 把 `Ado.IsEnableLogEvent` **按灭**（先在本机字段 `:544` 存一份旧值），装载结束再在 `:530` 恢复；收尾那一句走 `OnLogExecuted`（`:533`）。所以装载期间真实的驱动侧动作在它的 SQL 日志流里是**看不见**的。而 `:530` 那一次恢复**不在 `finally` 里**——装载一抛，开关就永久留在按灭态，本轮把这一笔量出来了，见 §2.13。FastSql 走的是另一条路：L1 那一档根本不产 SQL，产的是结构化的 `BulkReport`（`src/FastSql.Abstractions/Providers/Bulk.cs:46-54`：`Requested` 与 `Method` 分开记"要哪一层"和"实际走了哪一层"，再加 `RowCount`、`RoundTrips`、`ChunkSize`、`Degraded`、`Reason` 五颗）。§2.1、§2.3 那几行读数里的"7 块 ∶ 每块 315 行"来自与它同源的 `InsertPlan`（`Chunks`/`RowsPerStatement`/`ParameterBudget`），量具把两张单一起打了。

要说清的一件事：`OnLogExecuting` 这一条通道在 SqlSugar 里**同时装 SQL 和装载动作的叙述文本**，接钩子做审计的人会在同一支流里看到两种东西；FastSql 的 `Aop.Executed` 只装真实 SQL，装载另走 `BulkReport`。这是形状之差，不是对错之差——直到 §2.13 那一格，它变成了形状之差**加**一条可用性之差。

### 2.10 值里带单引号的一行

### 2.11 装载通道的地板

裸 `SqlBulkCopy`（自己造 DataTable，不经任何一家）：**19.91 – 31.25 ms**（把造 DataTable 的时间摘出去）／ **22.71 – 33.88 ms**（含造），六趟。更早那版本记的是 25.14／25.47 ms，落在同一量级里。本轮两趟里有一处**倒挂**要说清：`run-A` 给的是"只算复制 31.25 / 含造 28.62"，`run-B` 给的是"27.54 / 33.88"——那两条计时是各自三取最小的**两副独立活**，不是同一次的两个切片，所以"摘掉造表反而更慢"能出现。本文不据此说"造 DataTable 不花钱"，只把这格的用途守住：给 §2.1、§2.3 那几个 30+ ms 提供一个参照。

这一格存在的意义只有一个：**两家离地板都不远**——下界相减，FastSql L1 的 30.66 与对面装载的 28.97 各自比地板下界 19.91 高约 **11 与 9 ms**，所以装载通道这一档谁也没有把驱动的钱花掉第二遍。上界那一头（本家 123.55、对面 96.03）不在这个账上，那是跨趟长尾，本文没解释（§6 第一条）。

### 2.12 同一批活放进事务里，加上"身份列 vs 约束检查"那颗互斥

事务这一档先前只在 §3.3 读码、§6 挂着"没跑"，上一轮补了。**形制与别处不同**（§1 第 5 条）：计时段是 `begin → 写 → rollback` 整段，所以这一档只跟本档自己比，不跟 §2.1 论高低。`回滚后库里` 那一列是事务真生效的证据，不是装饰。四趟（上一轮两趟 + 本轮两趟）：

| 走法 | 墙钟（四趟） | 读数 |
| --- | --- | --- |
| FastSql L1 装载通道 ∶ 事务内 | **29.65 – 32.62 ms** | `CopyChannel ∶ 2000 行 ∶ 回滚后库里 0` |
| FastSql L3 多值 ∶ 事务内 | 1178.00 – 1343.60 ms | 7 块 ∶ 回滚后库里 0 |

**事务那一层两家都没有可见开销**：FastSql L1 事务内 29.65–32.62 与它事务外的六趟 30.66–123.55 同档（下界还更低，本文不解释，只报读数）；对面装载事务内 30.81–42.62 对它事务外的 28.97–96.03 同档。两边的区间都重叠，名次不报。**这一格本轮四趟里没有一个上界被越过**，它是全篇目前最"平"的一格（本家 1.10 倍、对面 1.38 倍跨度），而 §2.1 同一份活在事务外能抖到 4.0 倍——本文没有解释这一对反差。

然后是上一轮真正要钉的一颗开关。第五张表 `cmp_chk` 与窄表逐字相同，只多一颗 `CHECK (Amount >= 0)`，往里塞一行 `Amount = -5`。四趟里这五行**逐字相同**：

| 探针 | 结果 |
| --- | --- |
| SqlSugar ∶ 事务外 ∶ `OffIdentity()` 开 | 没报约束错 ∶ **违约行 1 颗进了库**（约束没查） |
| SqlSugar ∶ 事务内 ∶ `OffIdentity()` 关 | **被拒** ∶ `INSERT 语句与 CHECK 约束"CK_cmp_chk_Amount"冲突` ∶ 库里 0 |
| SqlSugar ∶ 事务内 ∶ `OffIdentity()` 开 | 没报约束错 ∶ **违约行 1 颗进了库**（事务内读到 1 颗，回滚后 0） |
| FastSql ∶ 事务外 ∶ L1 默认开关 | **被拒** ∶ 同一条 CHECK 冲突 ∶ 库里 0 |
| FastSql ∶ 事务内 ∶ L1 默认开关 | **被拒** ∶ 同一条 CHECK 冲突 ∶ 库里 0 |

三件事：

- **§3.2 那条"身份列与约束检查二选一"从读码结论升成实测。** 源码上 `SqlServerFastBuilder.cs:52-54` 那一支在事务内且 `OffIdentity` 开着时只传 `KeepIdentity`，于是 `:59` 的 `CheckConstraints` 没了——那五行里的第二、三行就是这一支的两半：不开 `OffIdentity` 时事务里查约束（违约被拒），开了就**不查**（违约行照样进库，还进了事务）。上一轮两趟与本轮两趟给的这两行逐字相同。
- **对面事务外根本不查约束**（第一行），这是 `SqlBulkCopy` 的默认语义（`CheckConstraints` 不在默认组合里），不是它的 bug；但它与 `OffIdentity` 叠出来的效果是**"带身份列的装载"在事务里也不查约束**，这跟"事务里就该被约束保护"的直觉相反。
- **本家的事务内外都被拒**：L1 恒传 `CheckConstraints | FireTriggers`，两颗位从驱动自己的枚举读（`SqlServerBulkCopy.cs:152-156` 的理由注释、`:208-217` 的 `Flags`），与是否在事务里无关，也没有一颗口能让你关掉它。这就是先前真库见证里"L1 与逐条等价"的行为来源，上一轮第一次从约束面上量到，本轮两趟复现同一对结果。

一句边界：这一档只用了 `CHECK` 一种约束，外键、唯一索引、默认值、计算列没试；`OffIdentity` 关 + 事务外的组合没测（那一支会因身份列而整体失败，与约束无关）；对面那条老的 `Insertable(...).ExecuteBulkCopy` 路径没测（§3.2 说它完全没有 KeepIdentity）。

### 2.13 走过装载之后，对面的 SQL 留痕还活着吗

这一格是上一轮翻车翻出来的：量具第一版把事务段放在中间，跑完之后**后面每一格对面的留痕全是空白**（`OnLogExecuting 响 0 次`、文本 `(无文本)`），一开始看着像对面"装载之后一直不留痕"，其实是一次异常把开关留在了按灭态。于是它被做成一节，每颗探针先把 `IsEnableLogEvent` 拨回 true 再走一步活，然后用一颗普通查询当探针数它响几次——**这样每一步的死活只属于那一步**。四趟（上一轮两趟 + 本轮两趟），四份输出的这一节逐字相同：

| --- | --- | --- |

**能读出来的只有这一条组合**：让日志停摆的不是装载、不是事务、也不是异常，而是**"事务内的装载抛异常"**这一支——它跳过 `FastestProvider.cs:530` 的恢复（`End` 不在 `finally` 里，调用链 `:497-506` 直排），把开关留在 `Begin`（`:545`）按灭的那一态；而且**它不会自己回来**：紧接着再来一次正常装载也不恢复（上一行倒数第二格），只有手动赋值能救。普通 `Insertable` 抛异常不影响它，纯事务开合也不影响它，两行都在这里验过。

对本家的意义写在两处：① 审计/留痕类调用方如果按"日志流有没有内容"判断连接健康，对面这一支会给出假绿（流断了，但连接照用）；② FastSql 的留痕没有这种全局开关可被掐——`Aop.Executed` 与 `BulkReport` 都是逐次调用交回的对象（§2.9），异常路径上不恢复任何状态。这是形状之差带来的可用性差别，不是对面配错了什么：它的 `IsEnableLogEvent` 本来就是公开可写的开关（`Interface/IAdo.cs:29`）。

一句边界：本轮只测了 `Fastest.BulkCopy` 一条装载口在事务内抛异常的形状（窄表 + `cmp_chk` 违约行），`BulkMerge`/`BulkUpdate` 那两支同样调 `Begin`/`End`、本文**没测**；`isLog` 那颗快照字段在多次嵌套装载下的行为也没测。

- **参数化那一族的身份是声明表，而声明表会跟着数据的位数走**：类型交给驱动推断时，同一批从 1 起的数（位数不齐）留 **5 颗、3 桶**，桶名就是 `nvarchar(3)/(5)/(6)` 配 `decimal(3,2)/(5,2)/(6,2)`；每副值都换到四位数起时只留 **2 颗**；把 `SqlDbType`/`Size`/`Precision`/`Scale` 钉死之后同样 2 颗但**只剩 1 桶**（`nvarchar(512)`/`decimal(18,4)`）。**"参数化 ⇒ 本文恒定"这句因此要打折，见 §5.7。** 墙钟那一头本文报不出差：推断那两族 1 247.45–3 073.81，钉死那一族 1 072.40–1 885.23，三副区间整个重叠。
- **两家 ORM 在服务端各留几颗**：本家 L3 **2 颗**（315 行的那块 + 110 行的那块），对面 `UseParameter` **1 颗**（每句都是 100 行，60 次执行全落同一颗）。颗数那一头的差**只来自分块形状**——本家 2 000 行除不尽 315，尾巴是一块 110 行，于是多一种本文；对面每句等长，就一颗。**这不是"谁绑定得更好"**，两家都不随值增计划，这正是 §2.6"参数化那一族换数据几乎不动"的机制半边。
- **声明表顺带把两家的绑定策略照出来了**：本家逐颗按值的宽度（`@p0 nvarchar(6)`、`@p5 nvarchar(3)`），时间给 `datetime2(7)`，小数给 `decimal(6,2)`；对面字符串一律 `nvarchar(4000)`，时间给 `datetime`（**不是 `datetime2`**）。前者把宽度写进身份，后者把宽度从身份里拿掉——上面那句"对面只留一颗"有一半是这么来的。`nvarchar(4000)` 与 `datetime` 会带来什么本文**没测**（本家用 `datetime2` 的理由写在它自己的源码注释里：默认的 `DbType.DateTime` 上线前会把值取整到 1/300 秒，`src/FastSql.Providers.SqlServer/SqlServerValues.cs:76-78`，对面的列声明是 `datetime2(3)`，所以本文无法从这格读数断言落库有差，只报形状）。
- **那些负数是量具的诚实，不是它的 bug**：`执行 -14 次`、`只跑过一次 -7` 都出现在这一台共享实例逐出计划、清零累计计数的时候（本轮八族里六族出现过负数）。它不影响"本族缓存现 N 颗"与那几行全文头（读的是此刻的状态），但把 `计划 +N` 那一列在没带标签的两族上打成不可用。

**三条口径限制**（读这一格必须先看清）：① `计划 +N` 只对**带本趟字母标签的六族裸 ADO** 成立；两家 ORM 的表名钉在实体类型上（`[Table("cmp_p6")]` / `[SugarTable("cmp_p7")]`），本轮没法加标签，于是它们的语句本文与上一趟逐字相同，`+N` 恒为 0——**这一行读不出"新增几颗"，只读"此刻占着几颗"**。② 探针只筛本文里含 `INSERT` 且含表名的语句，`TRUNCATE`、建表、清场都不进计数，但**同名的旧计划如果还没被逐出，会以"本族缓存现 N 颗"的形式混进来**（那两行 ORM 读数因此是"此刻缓存里"的颗数，不是"本轮产生"的颗数——本文按 18+3=21 与 60=3×20 两笔执行次数反查过，它们恰好等于本轮三副值的命令总数，所以这一格的两行可用）。③ 仍未抓 TDS，也没读编译耗时（`sys.dm_exec_query_stats` 不给这一项），"多一颗计划多花多少墙钟"本文只能从同一族的第 1 副与第 2、3 副之间的落差看（497–560 对 25–32 ms），拆不出编译、优化与逐出各自的份额。

## 5. 被这次对照翻掉、坐实或新钉住的旧说法

### 5.1 打折：规格里那句"SqlSugar 固定行数分块 ⇒ 受参数上限约束"

规格 `docs/fastsql-orm-design.md:1510` 那句话原文是：**"多值语句的参数个数 = 行数 × 列数。500 行 × 30 列 = 15000 参数 —— 在 DM/SQL Server 上直接爆。FreeSql / SqlSugar 都用固定行数分块，换宽表就出事。"** 前一半（我们自己的算法）没错，后一半这次对照下来要拆成两半说：

- **翻掉的是默认那一条。** 分块规则确实是固定行数（`SqlServerInsertBuilder.cs:34-42`），但默认路径把值全部内联（`:61` 走 `FormatValue`），那颗命令文本里**一颗参数都没有**（§2.1 的"参数 0 颗"），2100 这一关它进不去。所以正确陈述是：**SqlSugar 的默认批量不受参数上限约束，受的是"本文长度 + 服务端解析 + 计划缓存"的约束**——这三样里前两项上一轮量过（§2.5 那颗手拼对照：内联、每句 315 行、本文比参数化那一档还长，同数据 17.91–37.76 ms 跑完同一批活，比参数化那一档便宜一个数量级），第三项**这两轮量出来了，而且它是带条件的**：值一变，那颗手拼对照涨到 251.58–357.83 ms、对面自己的内联涨到 168.32–250.35 ms（§2.6）。所以那句纠正要写成：**默认路径不受参数上限约束，受的是"每趟的本文新不新"约束**；本文长度本身几乎不收钱（同数据下最长的那副反而最快），收钱的是复用不上计划。**本轮这一条还要再补一个条件：连"本文新不新"都取决于批大小**——服务端自己会把够小的内联本文折成参数化计划（每句 50 行那一族 120 句全落在同一颗上 ∶ 6 233 字节的本文被折了，315 行那一族约四万字节的主块没被折、只有它 110 行的尾巴那颗（13 853 字节）被折了 ⇒ 门限落在 6 233 与 13 853 字节之间，本文没量门限本身，§2.14 第二条），所以"内联付计划的钱"是大批次的性质，不是内联的性质。
- **坐实的是它另外那一条口，而且是从数上坐实的（窄表六趟、宽表四趟，§2.4）。** `Insertable(list).UseParameter()`（口在 `InsertableProvider.cs:519`）换到参数化实现，那里**确实**按 2100 分块：`ParameterInsertable.cs:129-132` 起点写死 100 行，`:171-187` 拿 `pageSize * count > 2100` 连压三档 50⇒20⇒10。实测两副表各给出一句不超过 2100 的形状（6 列实体 ⇒ 每句 100 行 / 600 颗；30 列 ⇒ 每句 50 行 / 1450 颗，§2.4）。所以"对面也有参数上限意识"这句不算冤枉它，只是**默认路径用不上**，并且它的问法是"撞不撞墙"而不是"多少行划算"。

规格这一轮**不动**（本轮没拿到记账例外），此处只把纠正落在本文，等下一轮再并回规格。

### 5.5 限定：先前写下的"对面真正拿不走的东西是内联"

### 5.6 翻掉：本文自己那句"FastSql 首页单条 `TOP n+1`"

本文上一版在它自己的 §2.6（分页那一格，本轮挪到 §2.7）与 §3.4 两处都写过本家首页发的是"单条 `TOP n+1`"。本轮读到了发射器，那句是**本文读歪的**：本家在 T-SQL 上**根本不产 `TOP`**——`SqlServerDialect.cs` 全文没有 `TOP`，分页只有一条路 `EmitPaging`（`:39-53`：`EmitPagingOrdering` + `OFFSET … ROWS` + `FETCH NEXT … ROWS ONLY`，缺省偏移落成常量 `0` 而不是省略子句，注释就写着"省略 OFFSET 会得到语法错"），既有金标 `tests/FastSql.Tests.Dialects/SqlServerPagingTests.cs:49` 钉的正是 `OFFSET 0 ROWS FETCH NEXT @p0 ROWS ONLY`。

所以正确的说法是：**首页一条语句没有错（本轮实测仍是 1 句、`Total` 为空、`HasNext` 为 True），但它的形状与第二页同形——`OFFSET @p0 ROWS FETCH NEXT @p1 ROWS ONLY`，`@p0` 是 0，`@p1` 是 `size + 1`。** 那句"多取一行探 HasNext"（`QueryEngine.cs:1225`）本身没错，错的是本文给它配的语法名。这一笔要翻的原因是它会误导读者去方言里找一颗不存在的 TOP 分支；可核性上也得说清：**首页那一句的原文本轮没抓到**（量具的样本袋在第二页之前清空了），这一句的根据是发射器代码 + 既有金标 + 第二页的实测文本三者一致，不是首页见证（§2.7 第一条已注）。

### 5.7 打折：本文那句"参数化 ⇒ 语句本文逐字不变"

§2.6 的整条因果链靠这一句撑着：值内联 ⇒ 每颗新本文要编译；值走参数 ⇒ 本文恒定、只换值。前半句本轮坐实了（§2.14 第一条），后半句被 §2.14 第三条**打折**：

**参数化保证逐字不变的是客户端那份 `CommandText`，不是服务端看见的那一份。** T-SQL 的参数化走 `sp_executesql`，计划身份是"本文 + 那颗声明表"，而声明表里的类型是**带长度的**（`nvarchar(6)`、`decimal(3,2)`）。量具把类型整个交给驱动推断：位数不齐的那一族（三副值同一批、从 1 起，`cmp_p4`）留出来的是 **5 颗计划、3 个桶**（`nvarchar(3)/(5)/(6)` 配 `decimal(3,2)/(5,2)/(6,2)`，§2.14 表格第 5 行），位数齐的那一族（每副值整体平移，`cmp_p3`）留 2 颗（第 4 行）；把 `SqlDbType`/`Size`/`Precision`/`Scale` 钉死之后，同样每副换值的活只剩 **1 个桶**（`nvarchar(512)`/`decimal(18,4)`，第 6 行 `cmp_p5`）。所以准确的说法是：**参数化把"值"从本文里拿走了，但只要类型靠推断，它就把"值的位数"放了回来**——一批 1 位到 6 位宽度不齐的数据，和一批清一色四位的数据，在服务端是两族不同的本文。

这一格在本家身上不是抽象的：`src/FastSql.Providers.SqlServer/SqlServerValues.cs:20-45` 的 `SizeOf` 对字符串取 `Length`、对 `byte[]` 取 `Length`、其余给 0，而 `:24-26` 的注释写着理由——**契约上的 `MaxChars` 会把实参截断，所以本家故意按实参长度报**。那颗 `Size` 随后原样搬进驱动参数对象（`src/FastSql.Core/Execution/AdoExecutor.cs:511-531` 的 `Bind`：`if (parameter.Size > 0) ado.Size = parameter.Size;`）。§2.14 第五条读数里那句"本家逐颗按值的宽度（`@p0 nvarchar(6)`、`@p5 nvarchar(3)`）"就是这条链在缓存里留下的影子。**也就是说：本家的服务端可见本文跟着数据宽度走，这是本家自己写下的策略，不是驱动的意外。**

对面在这一格上是另一种策略，同样从声明表读出来：`cmp_p7` 那一颗的声明是字符串一律 `nvarchar(4000)`、时间给 `datetime`（不是 `datetime2`）——**它把宽度从身份里拿掉了**，所以 2 000 行 × 3 副值 60 句全部落在同一颗计划上（§2.14 第四、五条）。本文对这一笔的表态到此为止：`nvarchar(4000)` 与 `datetime` 会不会带来存储或截断上的差，**本轮没测**（对面的列声明是 `datetime2(3)`，本家用 `datetime2` 的理由在它自己的注释里：`DbType.DateTime` 上线前会把值取整到 1/300 秒，`SqlServerValues.cs:76-78`），只报形状。

四处限制跟着这一句一起记：

1. **本文报不出这笔钱的价**：推断的两族（1 247.45–3 073.81）与钉死的那一族（1 072.40–1 885.23）墙钟区间整个重叠（§2.14 第三条末），所以"位数不齐 ⇒ 多几颗计划"是真的，"多几颗计划 ⇒ 慢多少"本轮没有读出来。
2. **fresh/same 那一档对照在参数化族上不干净**：本轮"每副换值"的族值都从四位数起 ⇒ 宽度齐 ⇒ 2 颗；"三副同一批值"的族从 1 起 ⇒ 宽度不齐 ⇒ 5 颗。**所以 p3/p4 那两行的差别读不出"换值"，只读得出"位数"**；干净的同值/换值对照只有内联那两族（p1 ∶ p2，同一批宽度、只有本文新不新不同）。这一笔是量具的构造缺陷，下一轮要把两件事分开，得让"换值"与"不换值"两族从同一个起点起。
3. **两家 ORM 那一格没有把这条坑走一遍**：本家 `cmp_p6` 那三副值同样从四位数起，所以它的声明表三副一样 ⇒ 2 颗（§2.14 第四条）。**"本家换一批位数不同的数据会不会多留几颗计划"本文没有实测**，它是从本家的绑定策略（上面那段 `SizeOf` + `Bind`）与裸 ADO 那两族的实测形状合起来的推论——推论的方向本文有信心（策略就写在那两行代码里），但颗数与代价没有见证。对面反过来被这一格帮了一次：它的 `nvarchar(4000)` 让宽度根本进不了身份。
4. **"要不要把契约长度/精度带进参数"因此是一条本家自己的调优方向，本文只报告**：它的落点在 provider 侧的值适配器（`SqlServerValues.CreateParameter`），不是在 `rowsPerRoundTrip` 那一档，也不是 §5.4 那条块大小的账。改它要么动契约语义（截断风险正是那句注释在防的东西），要么加一颗"按声明长度绑定"的开关——**两条都属于裁决，规格与台账本轮都没动，`src/` 本文一行没改**。而这一条的**收益本文没量到**（限制 1），所以它现在只是"形状上更少的桶"，不是一条可以推荐出去的优化。

一句自我修正的账：§2.6 上一版本就是拿"参数化那一族本文恒定"当无条件事实写的，本轮把它的客户端/服务端两半分开（§2.6 开头那句已经就地改成"服务端可见的那一份是否逐字相同，本轮才有答案"）。同族被本轮改口的还有 §5.4 那个倍数（8.4 → 6.6 倍）与 §5.8 那条"长尾只出现在对面"。

### 5.8 翻掉：先前写下的"跨趟长尾只出现在 SqlSugar 那两档"

## 6. 这次没量的，别当成比过了

- **跨趟长尾没解释，而且本轮确认它不认家**：SqlSugar 内联那一档四趟是 53.48 / 537.38 / 38.19 / 43.57 ms（§2.1），`Fastest.BulkCopy` 是 31.50 / 96.03 / 28.97 / 44.75，宽表那一档本轮多出一副 150.85（§2.3）；本家这一轮也出了一副——L1 装载通道 2000 行 × 7 列两趟是 **123.55 与 33.75 ms**（§2.1）。本文只把名次钉在区间下界，**没有诊断这一笔**（服务端忙、计划缓存被换掉、网络抖动三可；装载通道那一档连计划缓存都不进，所以那条解释对 123.55 不适用）。凡本文用"稳定"形容的档位，都是**那一格所有趟数**跨度在 21% 以内的那些——先前按这句话划出来的名单要重划，见 §5.8。
- **参数代价的曲线只取了四个点**（每命令 120 / 300 / 600 / 1890 颗），而且只在 6 列表上扫；指数约 1.7 是两点拟合，**不是定律**，也没在别的列宽下验证。宽表那一副只量了默认档（每块 65 行 / 1 885 颗）与 L1，没在 30 列上扫过行数。
- **曲线归谁没分离干净**：§2.5 那颗裸 ADO 对照只证明"不在 FastSql 这一层"。驱动侧的参数序列化与服务端侧的参数解析各占多少，本文没量（要分开得抓 TDS 或比 `SET STATISTICS`）。手拼那一族的"参数没设类型与长度"这一处本轮单独做了一族（`cmp_p5`，钉死 `SqlDbType`/`Size`/`Precision`/`Scale`），结果只读得出**形状差**（5 桶 ⇒ 1 桶）读不出**钱**（三族墙钟区间整个重叠，§2.14 第三条）——所以"绑定策略不同会贵多少"本文仍然没有数。
- **"换数据"那一节的机制半边本轮补上了，剩下的三笔没补**（§2.6 → §2.14）：计划颗数、`objtype`、声明表、全文长度与行数是直接读 `sys.dm_exec_cached_plans` 系列视图读出来的，但**仍未抓 TDS，也没读编译耗时**（那组视图不给这一项），所以"多一颗新计划 ⇒ 多花多少墙钟"只能从同一族第 1 副与第 2、3 副的落差看（497–560 对 25–32 ms），拆不出编译、优化与逐出各自的份额。另外三笔：① 只试了"每趟全换"，没有"每两趟换一次"这种中间档，部分复用下的曲线本文不知道；② 换数据同时改变了写入的值本身（数字位数、字符串长度、页与索引的分配状态），这一笔与编译那一笔混在一起，本文无法定价——而 §2.14 反过来还发现**位数本身就会改服务端可见的本文**（声明表，§5.7），所以这两笔的纠缠比上一版写的更深；③ 那八族里"换值"与"同值"两族起点不同（四位数起 vs 从 1 起 ⇒ 位数齐 vs 不齐），所以参数化族的 fresh/same 对照**读不出换值的钱**，只有内联那两族是干净对照（§5.7 第 2 条）。裸 ADO 参数化那一档换数据之后还**更快**（1 104.31–1 482.67 对 1 299.55–1 706.45），本文不解释。
- **计划缓存那一侧还有三件没量的事**：① **服务端自动参数化的门限**只夹在 6 233 与 13 853 字节之间，门限本身没扫（要扫得造一批不同行数的内联批次，本文没有）；它是否与兼容级别、`optimize for ad hoc workloads`、实例配置有关，本文一概没查。② 两家 ORM 那两族**没能加字母标签**（表名钉在实体类型上），所以它们的 `计划 +N` 列不可用，两行读的是"此刻占着几颗"，靠执行次数反查对齐（§2.14 口径限制①）。③ 参数嗅探、计划引导（`OPTION (RECOMPILE)` / `OPTIMIZE FOR UNKNOWN`）、`sp_executesql` 的语句模板化，本文全都没碰——本轮只数了颗数与形状，没评价任何一颗计划的**质量**。
- **内联那一档本文是手拼的，不是从对面嘴里拿的**：`§2.5` 那颗 17.91–37.76 ms（同数据）与 251.58–357.83 ms（换数据）的对照出自量具自己的裸 ADO 实现，对面真实实现另有它的转义与列类型分岔（§2.10）。所以"本家该不该做内联"这一问，本文只给了量级，**没给可行性**——安全责任在转义函数身上这件事，见 §2.10 那笔取舍。本轮新增的那颗条件（小块内联被服务端折成参数化计划，§2.14 第二条）同样只在手拼那一族上量到，对面真实实现会不会撞上同一道门限，本文没测。
- **装载的两笔一次性开销都被计时纪律挑掉了**：SqlSugar 首趟的"向库里要空表壳"与 FastSql 首次的反射装载。要量稳态之外的那一笔，得改成"取第一趟"重跑。
- **事务与装载只跑了最窄的一格**（§2.12）：`begin → 整批装载 → rollback` 的墙钟与"回滚后库里 0"，加一颗 `CHECK` 约束、三颗对面开关组合、两颗本家默认。没跑的还有：嵌套事务里的装载、`RequiresNew` 下的装载、`Fastest.Size` 分批与事务的叠加（对面那一支每批自开事务，`FastestProvider.cs:63-74`）、对面老的 `ExecuteBulkCopy` 路径、唯一索引/外键/默认值/计算列、并发写下锁与阻塞的形态，以及"违约行进库"那一支在真业务表上会带来什么（本文只证明它能进，没有评价该不该）。

- **一台实例、一组数据形状、每格两到六趟（`UseParameter` 窄表八趟）、每趟三取最小**：换实例、换列类型（`varchar(max)`、`datetime2`、`sql_variant`）、换批量大小都可能换结论。§2.6 那一节从两趟补到了四趟，但它的整个论点仍然是"跨趟的相对变化"，不是某一格的绝对值；§2.14 那一格比它还薄——**它是两趟**，而每族的三副值只在**同一台共享实例的当前缓存状态**上读数（本轮八族里六族出现过负的 `执行 +N`，那是服务端逐出计划，§2.14 第六条），换一台热的实例、换一种缓存清理节奏，那两列都可能不一样。

## 7. 这份文档怎么被维护

- 想更新数字：跑 §1 的量具**连跑两趟**（`run-A.txt` / `run-B.txt`，别忘了给这一趟取一个字母标签），把每格的两趟读数与文档里现有的区间**取并**写成新范围，并**在格子里改趟数标注**（本轮就有四格从"四趟"变"六趟"、一格从"六趟"变"八趟"、四格从"两趟"变"四趟"，另新开一格 §2.14），**保留每格的"读数"原文**（那才是可核的东西，毫秒数只是它的摘要）。只跑一趟就更新数字，等于把抖动作成精度。
- **凡是读服务端状态的格子，标签是硬要求**：`3g` 那一段靠 `sys.dm_exec_cached_plans` 读数，而计划缓存是**按语句本文**归户的——两趟用同一批表名 ⇒ 两趟的本文逐字相同 ⇒ `计划 +N` 整列读成 `+0`（本轮第一版就是这么读的）。所以每一趟建表都要带字母后缀（`cmp_p1d` / `cmp_p1e`），清场也要按带标签的名字清；同时**一族必须一张表**，否则"这一族留了几颗计划"要按本文猜主语。还有一条本轮学到的顺序：那三列全文探针（本文字节数、行数、执行次数）**必须紧跟在本族的形状探针之后**，晚一步就会被下一族的本文混进来。
