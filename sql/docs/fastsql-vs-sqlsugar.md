# FastSql 与 SqlSugar 对照

> 这份文档只做一件事：把 FastSql 与 SqlSugar 放在**同一台真库、同一副表、同一批活**上比，并且把每个结论钉到可核的出处上。
>
> 设计论证在 `docs/fastsql-orm-design.md`（规格），日常用法在 `docs/fastsql-orm-usage.md`（用法）。本文不是第三份设计文档，也不改那两份的口径。

## 1. 量具与重跑法

量具是一次性控制台工程，放在 **`sql/obj/sqlsugar-compare/`**（`obj/` 被 `sql/.gitignore` 挡住，不进版本库）：

- `Program.cs`：**十七段对照活**（1–10 十段，另加 `3b`…`3g` 六段与 `10b` 一段 ∶ 批量、逐条、宽表、`UseParameter`、颗数因果、每语句行数扫、裸 ADO 对照、**每趟换一批全新值的同一形状**、**计划缓存那一侧的直接读数（DMV）**、分页首页与第二页、读物化、留痕次数、引号、地板、**留痕存活探针**、**事务内装载与约束二选一**）；
- `fscompare.csproj`：`SqlSugarCoreNoDrive` 5.1.4.218 + `Microsoft.Data.SqlClient` 7.1.0 + `ProjectReference` 到工作树的 FastSql 三颗程序集，并挂 `FastSql.Generators` 为 Analyzer（否则消费者程序集里没有 G2 注册表，`FastSqlOrm.Create` 会报"DbKind.SqlServer 未在 ProviderRegistry 中登记"）；
- `run.txt`：最近一次跑出来的原始输出；`run-A.txt` / `run-B.txt`：**本轮同一份二进制连跑两趟的原始输出**（标签 f 与 g，两趟各带一个字母标签，见下）；`run-prev-d.txt` / `run-prev-e.txt`：上一轮那两趟（标签 d 与 e）的原文，本轮重跑前抄下来的——§2.14 原八族因此四趟都有原文可对，但它们同样住在 gitignored 目录里，下一轮重跑会覆盖。

**标签是上一轮加的一条纪律**：`fscompare.exe f` / `fscompare.exe g` 这样传一颗字母参数，§2.14 那十三族裸 ADO 的表名就跟着变成 `cmp_p1f`…`cmp_p15f`。原因是计划缓存的**键是语句本文**：上一趟与这一趟的表名相同时，本文也相同，于是 `计划 +N 颗` 整列读成 `+0`（第一版就是这么红的），一个字的标签把两趟隔开。

**读数的出处怎么算（八趟，四份原始文件 + 一份旧文档）**：本节表格里写"八趟"的区间，下界与上界由各副读数钉住 ∶ 在工作树里可直接开的 `run-A.txt`/`run-B.txt`（标签 **f ∶ g**，本轮连跑的两趟）与 `run-prev-d.txt`/`run-prev-e.txt`（标签 **d ∶ e**，上一轮连跑的两趟，本轮重跑前抄下来的），以及更早那两版文档（提交 `2415164` → `d22ac08`）里那四趟留下的区间。最早那四趟的原始输出**不在版本库里**（`sql/obj/` 被 gitignore 挡住），上一轮重跑时已被覆盖，所以它们的读数只以区间形式存在于 `git show d22ac08:sql/docs/fastsql-vs-sqlsugar.md` 的表格里——这是一条**降级了的可核性**，本文照实写在这里。本轮新增的格子（§2.14 计划缓存）里那七族只有两趟（f ∶ g），原八族升到四趟（d ∶ e ∶ f ∶ g），格子里的标注已跟着改。**轮的称呼**：本文从本轮起"本轮"只指 **f ∶ g** 这一对，往前的轮次一律用标签或提交号称呼 ∶ `d ∶ e` = 提交 `4fb6217`，更早那一轮 = `d22ac08`（它开出 §2.6、§2.12、§2.13 并翻出那次段序翻车），最早那四趟 = `2415164` 时代。§2.1–§2.14 与 §3–§7 的正文大多写于 `d ∶ e` 那一轮、个别更早，那些句子里的"本轮/上一轮"当时指的是它们自己那一轮；本轮并数时凡是被新读数碰到或改口的句子都就地换成了标签（`f ∶ g`、`d ∶ e`、更早那一轮），没碰到的句子仍按它写下的那一轮读，`§7` 末条把这套称呼钉住了。个别形状在量具里出现在两处（`UseParameter` 的 2000×6 在 `3b` 与 `3d` 各跑一次），那种格子本文写出实际趟数（最宽的一格十二趟）。

重跑（已验：从该目录 `dotnet build` 成功）：

```powershell
cd E:\Resource\Fast\sql\obj\sqlsugar-compare
dotnet build -v q --nologo          # 0 警告 0 错误
$env:FASTSQL_DRIVERS_CONFIG = "E:\Resource\Fast\sql\FastSqlDrivers.json"
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()   # 不清这行，控制台见证会是 GBK
bin\Debug\net10.0\fscompare.exe d | Out-Null; Copy-Item run.txt run-A.txt   # 标签 d
bin\Debug\net10.0\fscompare.exe e | Out-Null; Copy-Item run.txt run-B.txt   # 标签 e：两趟的表名不同名，§2.14 的计数才作数
```

连接串的取法和集成层判据同一条：`FASTSQL_TEST_CONNECTION` 优先，其次 `sql/fastsql-test.connection.local.txt`（本地文件，gitignored）。量具全程不打印口令。

**段序是硬的**：`9`（留痕存活探针）与 `10`/`10b`（事务×装载）必须排在所有量墙钟的格子之后。这不是排版偏好——更早那一轮（提交 `d22ac08` 那版）的第一版把事务那几段放在中间，跑出来的 `run.txt` 里**后面每一格对面的留痕全成了空白**（`OnLogExecuting 响 0 次`、`(无文本)`），因为事务内装载抛异常会把 `Ado.IsEnableLogEvent` 按灭且不恢复（§2.13 就是这一笔翻出来的证据）。这次翻车留着，因为它同时是结论和排雷图。

**计时纪律**（五处容易做假的地方，都堵上了）：

1. 每格取**三趟最小值**；
2. 计时段**只包住活本身**，`TRUNCATE`、建连接、建表都在计时段外——这条不是洁癖：早前一版把 `TRUNCATE` 算进去了，量出 FastSql L1 207 ms 对 SqlSugar 38 ms 的 5 倍差距，重排之后两家在同档（八趟区间 30.66–123.55 对 28.97–96.03，下界差 1.7 ms，§2.1）；
3. 表里的"句"指**一次命令文本**（一次 `ExecuteNonQuery`）。SqlSugar 的分块会把多段 `INSERT` 用 `;` 串进同一颗命令文本里，所以"1 句"**不等于**"1 条 INSERT"，本文在下面会写清到底几段。
4. **本节绝大多数毫秒数是八趟完整跑的区间**（来历见上上段），不是单趟。这一条也是被数据教的：同一格跨趟能从 38 ms 跳到 537 ms（§2.1 的 SqlSugar 内联那一档），d ∶ e 那一轮又添一副 33.75 跳到 123.55（§2.1 的**本家** L1 那一档），单趟报出来的任何一位小数都会假装精度比实际有的高。区间下界用于排名次，上界用于说"抖多大"；**两副区间重叠的格子，本文不再排名次**（据此收回的名次累计到 **七处**：§2.8 那句"对面稳定快约 10%"、§2.5 中间两档的排序、§2.1 那句"长尾只出现在 SqlSugar 那两档"（d ∶ e 轮翻的，见 §5.8），再加本轮 f ∶ g 并数时翻的四处 ∶ §2.5 的"手拼 ADO 比 FastSql 还略慢"、§2.6 的"裸 ADO 参数化换数据反而更快"、§2.8 的"四副配对没有一副是本家胜"、§2.12 的"这一格没有一个上界被越过"——见各格）；新增的格子从一开始就按这条办——§2.2 的配对一比一、§2.12 的墙钟、§2.14 的每族墙钟都不报名次）。
5. **§2.12 那一档的形制与别处不同**：它把 `begin → 写 → rollback` 整段计时，而别处只计"写"，所以那一档只跟同形制的那一档比，不拿来跟 §2.1 论高低。

## 2. 实测：十四格原始读数

### 2.1 批量插入 2000 行 × 7 列

| 走法 | 墙钟（八趟） | 留痕读数 |
| --- | --- | --- |
| FastSql L1 装载通道 | **30.66 – 123.55 ms** | `CopyChannel ∶ 2000 行 ∶ 1 次递交 ∶ 库里 2000` |
| FastSql L3 多值语句 | 1176.07 – 1617.09 ms | `MultiValue ∶ 7 块 ∶ 每块 315 行 ∶ 语句 7 句 ∶ 参数 12000 颗 ∶ SQL 文本累计 93263 字` |
| SqlSugar `Fastest<T>().BulkCopy` | **28.97 – 96.03 ms** | `OnLogExecuting 响 1 次 ∶ 参数 0 颗 ∶ SQL 文本累计 79 字 ∶ INSERT 0 段` |
| SqlSugar `Insertable(list)` | 38.19 – **537.38 ms** | `OnLogExecuting 响 1 次 ∶ 参数 0 颗 ∶ SQL 文本累计 328580 字 ∶ INSERT 10 段` |
| 裸 `SqlBulkCopy`（地板，§2.11） | 19.91 – 31.25 ms（只算复制） | 库里 2000 |

（"每句 315 行 × 2000 行"这一副 FastSql 的活在量具里出现在两处（本节的 `1` 与 `3d`），每处各八趟，合起来十六副读数，跨度 1 176.07 – 1 617.09 ms（比 38%）。两处各写自己那八趟的区间，不混成一副。）

SqlSugar 批量那一档写出去的形状（原文截断）：

```sql
INSERT [cmp_sugar]  ([CustomerName],[CustomerId],[Amount],[State],[CreatedAt],[Note])
   SELECT N'客户1' AS [CustomerName],N'7' AS [CustomerId],1.25 AS [Amount],N'1' AS [State],'2026-10-05 01:02:03.000' AS [CreatedAt],N'cmp' AS [Note]
   UNION ALL
   SELECT N'客户2' ...
```

五个读数要合起来读：

- **装载通道这一档两边打平，而且这一格八趟区间整个重叠**：FastSql 30.66–123.55，SqlSugar 28.97–96.03，下界差 1.7 ms；上界 d ∶ e 那一轮反过来是本家更高（123.55 那一趟就是下面那条长尾）。地板（§2.11）在 19.91–31.25，所以两家各自都有约 **9–11 ms** 的"把自己那层套上去"的开销（下界相减），这一层两家同量级。
- **这一格第一次给到了"段数"而不是只有"句数"**：留痕里那句 `INSERT 10 段` 是在 `OnLogExecuting` 里数 `INSERT ` 关键字的颗数量出来的（先前版本此处写"按 `SqlServerInsertBuilder.cs:34-42` 推得 10 段"，那一档现在坐实了：2000 行 ÷ 每段 200 行 = 10 段，与推算逐字相同；d ∶ e 与 f ∶ g 各两趟都是 10 段）。
- **SqlSugar 的批量默认根本没走参数**：参数 0 颗、文本 32.8 万字，值全部内联成字面量，**一次往返**送出去。这条读数直接打折一句旧说法，见 §5.1；而它的**红利条件**是更早那一轮（提交 `d22ac08` 那版）量出来的，见 §2.6。
- **长尾这一笔不认家**：先前在这一格写下的是"**长尾只出现在 SqlSugar 那两档**"，d ∶ e 那一轮被本家自己的一趟否掉了——FastSql L1 那两趟是 **123.55 与 33.75**（3.7 倍），把它并进更早四趟的 30.66–36.81 就是 30.66–123.55。同一份二进制、同一副表、同样是三趟取最小，本家这一档一趟能涨到三倍多。对面那两档照旧（`Insertable(list)` 更早四趟 53.48 / 537.38 / 38.19 / 43.57，d ∶ e 是 44.46 / 38.51；`Fastest.BulkCopy` 31.50 / 96.03 / 28.97 / 44.75，d ∶ e 是 35.80 / 39.12）。跨度于是变成：本家 L1 **4.0 倍**、L3 1.37 倍，对面装载 3.3 倍、内联 14 倍——**"本家比对面稳一个量级"那句也跟着作废**，只剩"对面内联那一档跨度最大"还站着。本文**没有解释任何一副长尾**，只把量程报出来，并把名次钉在"下界"上（见 §6 第一条、§5.8）。
- **f ∶ g 这两趟没有越出这一格的任何一副区间**（本家 L1 36.62 / 33.71，本家 L3 1 207.23 / 1 472.30，对面装载 36.36 / 38.11，对面内联 49.80 / 44.42，地板那一行见 §2.11），所以六趟区间与八趟区间**逐字相同**。这一格因此是全篇少数"并了两趟、区间一位没动"的格子，本文把它单独记一句：那几副上界（123.55、537.38、96.03）不是被新一轮抬高或被新一轮压低出来的，它们到现在为止只出现在 d ∶ e 与更早的那几趟里。
- **文本量是另一笔账**：同一批活 SqlSugar 写出 328,580 字，FastSql L3 写出 93,263 字加 12,000 颗参数。内联换到的是"不付参数的钱"（§2.5 量到了这一笔有多大），付出的是"服务端要为 33 万字的语句本文做编译"——这一笔先前只挂在"没量"那一栏，更早那一轮量了（结果是它会改名次，见 §2.6），`d ∶ e` 那一轮又把它换成**服务端侧的直接读数**（§2.14：那 33 万字里每一句都留下一颗计划），本轮（f ∶ g）再给它钉上一道批大小门限（§2.14 第二条）。

### 2.2 逐条插入 500 行

| 走法 | 墙钟（八趟） | 更早四趟给过的读数 |
| --- | --- | --- |
| FastSql 逐条（`SingleRow`） | 282.31 – 380.44 ms | 302.07 / 307.27 / 335.22 / 365.24 |
| SqlSugar `Insertable` 单条循环 | 296.62 – **367.57** ms | 327.99 / 337.18 / 349.44 / 358.90 |

**持平，而且这一格的"持平"是量出来的、不是抹平的**：f ∶ g 这两趟的配对同样是量具在同一趟里记下的——**348.23 对 322.84 对面快 7.3%，282.58 对 320.50 本家快 11.8%，又一比一**。d ∶ e 那一轮给的是 317.91 对 367.57 本家快 14%、369.98 对 356.32 对面快 4%（也一比一），更早那两趟给的是 282.31 对 339.19、348.85 对 340.22（同样一比一）。**三轮六副同趟配对，每一轮都是一副本家快、一副对面快**，没有一轮出现过"两副同向"——这一格从"区间重叠所以持平"升级成"配对层面也是一个对一个"。再往前那两趟只留下了区间和一副明确配对（380.44 对 296.62，对面快 22%），另一副本文不配对、不猜。最早的四趟（302.07 / 307.27 / 335.22 / 365.24 对 327.99 / 337.18 / 349.44 / 358.90）只能按大小顺序假定配对，那一半本家快 4–9% 三副、对面快 2% 一副——**这个"按序配对"是推的，不是量的**，本文只当参考。回到能主张的那一半：两副区间 282.31–380.44 与 296.62–367.57 大面积重叠（d ∶ e 那轮对面的上界从 342.85 抬到 367.57，f ∶ g 两趟 322.84 / 320.50 都落在重叠带里，区间一位没动）。这一格两边都走参数化单条语句，量的其实是"一次往返多少钱"（约 0.6–0.8 ms/条），谁的内核都省不掉。

### 2.3 宽表 30 列 × 500 行

| 走法 | 墙钟（八趟） | 读数 |
| --- | --- | --- |
| FastSql `Auto`（不调 `WithBulk`） | **27.24 – 47.15 ms** | `Auto→CopyChannel` ∶ 1 次往返 ∶ 库里 500 ∶ `Reason` 原文是"500 行走 SqlServer 的装载通道（§12.1 的 L1）：不发 SQL 文本、不走参数，一次递交。通道内部怎么分批是驱动的事，对上层是一次递交一块；改写类钩子（`CudBuilding` / `ParameterBinding`）在这一档不适用" |
| FastSql L1 装载通道 | **30.84 – 39.12 ms** | `CopyChannel ∶ 500 行 ∶ 1 次递交 ∶ 库里 500` |
| FastSql L3 多值 | **1460.33 – 1949.06 ms** | 8 块 ∶ 每块 65 行 ∶ 每块参数 1885 颗 ∶ 库里 500 |
| SqlSugar `Fastest.BulkCopy` | **30.51 – 38.50 ms** | 响 1 次 ∶ 参数 0 颗 ∶ 文本 83 字 ∶ INSERT 0 段 ∶ 库里 500 |

### 2.4 SqlSugar 的参数化那一条口：`UseParameter()`

先前版本的 §3.1 与 §5.1 说"对面也有参数上限意识，只是默认路径用不上"——那句**只有源码没有数**。d ∶ e 那一轮把它跑了，本轮 f ∶ g 又跑了两遍（`UseParameter` 的窄表那副活在量具里出现在 `3b` 与 `3d` 两处，两处各六趟、合起来十二趟；宽表那副只在 `3b` 一处，八趟）：

| 走法 | 墙钟 | 读数 |
| --- | --- | --- |
| `Insertable(2000 行).UseParameter()`（6 列实体） | **403.57** – **943.33** ms（**十二趟**） | **20 句 ∶ 每句 100 行 ∶ 每句 600 颗 ∶ 总参数 12000 颗 ∶ 文本累计 159,700 字 ∶ INSERT 20 段** |
| 同上，宽表（30 列实体） | **1224.96** – 1579.77 ms（八趟） | **10 句 ∶ 每句 50 行 ∶ 每句 1450 颗 ∶ 总参数 14,500 颗 ∶ 文本累计 124,010 字** |

写出去的是真参数化多值，参数名每句重新编号（原文截断）：

```sql
INSERT INTO [cmp_sugar]  ([CustomerName],[CustomerId],[Amount],[State],[CreatedAt],[Note])
VALUES(@CustomerName0,@CustomerId1,@Amount2,@State3,@CreatedAt4,@Note5),  (@CustomerName6,@CustomerId7, ...)
```

源码那一档与实测逐字对上（`ParameterInsertable.cs:111,129-132,171-187`）：起点是**写死的 100 行**，然后按 `pageSize * count > 2100` 连压 50⇒20⇒10，而那颗 `count` 是**实体列数（含自增列）**——所以 6 列实体（含 `Id` 共 7 列）是 7×100=700 ≤ 2100、不压，量到每句 100 行；宽表（含 `Id` 共 30 列）30×100=3000 > 2100、压到 50，实发每行 29 颗 ⇒ 1450。**每一句都压在 2100 以下：这一点先前只读到判据、没量到落地，现在量到了。**

但它与 FastSql 的分别也一并清楚了：**2100 对它是一道墙，不是一个目标**。100 行 × 21 列 = 2100 刚好不压，22 列才压到 50 行——它从不问"这一句多少行花多少钱"，只问"撞不撞墙"。而 FastSql 的 §12.3 公式问的也只是预算（`ParameterBudget * 9 / 10 / cols`），所以两家在这件事上是**同一种问法**，只是默认答案不同：2100 的九成 ⇒ 贴着曲线贵的那一端，100 行 ⇒ 贴着便宜的那一端。谁都没把"每命令颗数的超线性代价"放进目标函数（§2.5、§5.4）。

### 2.6 同一批形状，每趟换一批全新值：把"计划能不能复用"这一笔摘出来

**这一节是更早一轮新开的，它改写了 §2.5 第 2 条的成立条件；d ∶ e 那一轮把它的趟数从两趟补到四趟，本轮 f ∶ g 再补一趟对（换数据那一列现在六趟、同数据那一列八趟），并把"机制那一栏"从空白换成直接读数（§2.14）。** 前面所有格子都跑在同一批数据上：三趟计时用同一副值，于是内联那一档每趟写出去的是**逐字相同的一大坨本文**——服务端第一次编译过之后，后面两趟复用的是什么，本文先前没有区分过。量具的做法是把值整体平移（每趟 `shift += 1000`，`Cell` 的 prep 里递增 ⇒ 三趟是三批互不相交的数据），形状、行数、颗数一颗都不动，只让"值"变。参数化那一族的**客户端**语句本文因此照旧逐字相同（服务端可见的那一份是否逐字相同，d ∶ e 那轮才有答案，见 §5.7），而内联那一族的本文每趟都是新的（长度只差千分之几）。下表左边是八趟、右边是六趟：

| 同一副活 | 每趟同数据（八趟） | 每趟换数据（六趟） | 换数据带来的差 |
| --- | --- | --- | --- |
| SqlSugar 内联 ∶ 每段 100 行 | **52.63 – 67.83 ms** | **168.32 – 260.06 ms** | 慢 **3.2 – 3.8 倍**（同界相除；先前那副上界 250.35 对 57.09 给的是 4.4 倍，本轮两边各抬一档，比值收窄） |

| FastSql L3 ∶ 每句 315 行（1890 颗/句） | 1215.39 – 1404.67 ms | 1093.42 – 1513.95 ms | 两副区间互相包住 ⇒ 涨没涨报不出 |

- **内联的便宜是"同一批数据"租来的。** 值一变，对面默认那条口从 53–68 ms 档掉到 168–260 ms 档，手拼那条更从 18–38 ms 掉到 252–373 ms；而参数化那一族（两家加手拼三副）换数据几乎不动。这与 §2.5 的因果链是同一条：语句本文里带字面量 ⇒ 每颗新本文都要服务端编译；带参数 ⇒ 本文恒定、只换值。**d ∶ e 那一轮这一条不再只是推的**——§2.14 直接数到了：手拼内联那一族每副值留 **19 颗计划**，同一批值三副只留 **7 颗**，而后者第二、三副的墙钟是 19.10–32.13 ms（前一副 270.22–567.82 ms）。
- **名次随之改写**：同一批 2000 行 × 6 列，换数据之后本家最便宜的形状（每句 20 行）下界 **165.10 ms**，对面内联（每段 100 行）下界 **168.32 ms**——**本家反超 2%**，而两副区间（165–226 对 168–260）几乎完全重叠（本轮 f ∶ g 只动了对面的上界，下界一副都没换，所以这一句的数不变）。所以"内联这一档 FastSql 拿不到"那句，在同数据条件下成立（3.9–40.7 倍，§2.5 第 2 条），在换数据条件下只剩"对面默认比本家默认便宜"（168 对 1 093，本家的默认块仍然贴墙，见 §5.4），不再是"便宜一个数量级"。
- **本家默认那一条仍然被自己的块大小坑**：它换不换数据都在 1 093–1 514 ms，而 `rowsPerRoundTrip: 20` 那一条 151–226 ms。这一格反过来给 §5.4 加了一句：**贴墙的块不只贵在内联对不过，它连"换数据"这一关都不需要对面帮忙就自己输了 6.6 倍**（下界 1 093.42 对 165.10；更早那版按 1 388.55 算出的那句"8.4 倍"因为 d ∶ e 那一副更低的下界作废，§5.4 已就地改口，f ∶ g 没有再动这两个数）。

口径要钉死的一处：更早那一轮这一节**没有**直接读服务端的计划缓存（没查 `sys.dm_exec_cached_plans`，也没抓 TDS），"编译 vs 复用"是从"只有内联那一族变动"这一条对照推出来的——那时候本文把它写成**与源码形状一致的读数**，不是机制的证明。d ∶ e 那轮的 §2.14 把计划那一侧数到了，这一节因此升成"有机制读数为证的后果读数"；**仍未抓 TDS**，而"命中"与"重新编译"之间的服务端动作本文还是看不见（§6）。更早那一版在这里写过"还有两点没试"，其中一点 d ∶ e 轮之后、本轮补齐了：**"每两趟换一次"这种中间档量到了**（§2.14 第二张表最后一行 `cmp_p15`，只有 f ∶ g 两趟），答案是台阶不是梯度——复用得上的一副值 **29.41 – 33.74 ms**，换新值的两副 **417.64 – 572.12 ms**（同一族里 rep1 与 rep3 都是新值，rep2 复用 rep1 那批），没有"半新半旧打对折"那一级。剩下那一点没补：每趟全换也让索引与 page 分配的状态变了，本文无法把这一笔从编译那一笔里剥干净；而本轮新量到的门限又给它加了一条 ∶ **同一族内每句行数一旦跨过 160–170 行那一道，"换值要不要付钱"这件事本身就换了规则**（§2.14 第二条），所以这一节的六趟区间只在"每句 315 行"这一个形状上成立。

SkipTotal : CountStar`），也就是两条——**这条换档更早一轮只报源码、上一版实测到了，f ∶ g 再跑两趟还是同一形状**：第二页确实发两句，`Total` 也从 null 变成 200。要总数必须显式换 `CountMethod`（`src/FastSql.Abstractions/Query/IQuery.cs:19` 的 `PagedOptions` 默认 `CountMethod.Auto`）；`CountOverWindow`（单往返带总数）与 `SeparateTransaction`（同连接同事务两条）**今天直接抛异常**，不是静默降级。SqlSugar 的 `ref total` 是"要总数就固定两条语句"——`QueryableExecuteSql.cs:509` 那一档写得很白：先 `this.Clone().Count()` 再 `this.Clone().ToDataTablePage(...)`，两次往返、两次 `Clone()`。两边各有对面拿不到的东西：SqlSugar 拿不到"不写 `ref total` 之外还能选单往返带总数"，FastSql 拿不到默认给的准确总数。

六趟抓到两家第二页写出去的东西（每一趟的文本逐字相同；工作树上那四份原文 `run-prev-d/e`、`run-A/B` 里这一节连语句数带文本都是一字不差），形状差得比想象中远：

```sql
-- FastSql ∶ ToPagedAsync(2,20) 的两条语句
SELECT [t0].[Id], [t0].[CustomerName], … , [t0].[Note] FROM [cmp_fast] AS [t0]
  ORDER BY (SELECT NULL) OFFSET @p0 ROWS FETCH NEXT @p1 ROWS ONLY
SELECT COUNT(*) FROM [cmp_fast] AS [t0]

-- SqlSugar ∶ ToPageList(2,20) 不要总数的那一条
SELECT * FROM (SELECT [Id],[CustomerName],…,[Note],ROW_NUMBER() OVER( ORDER BY GetDate() ) AS RowIndex
               FROM [cmp_sugar] ) T WHERE RowIndex BETWEEN 21 AND 40
```

三读数合起来：

- **本家在 T-SQL 上从不发 `TOP`，先前本文那句写错了**：第二页真发的是 `OFFSET…FETCH`（`SqlServerDialect.cs:39-53` 的 `EmitPaging`，缺省偏移落成常量 `0` 而不是省略子句），而首页那一档**同形**——本家没有 TOP 发射器（`SqlServerDialect.cs` 全文搜不到 `TOP`，方言册既有金标 `tests/FastSql.Tests.Dialects/SqlServerPagingTests.cs:49` 钉的就是 `OFFSET 0 ROWS FETCH NEXT @p0 ROWS ONLY`）。先前版本在 §2.6 与 §3.4 两处写下的"单条 `TOP n+1`"是本文读源码读歪的，上一轮翻掉，见 §5.6。首页那一句的**原文**当时没抓到（`fastSamples` 在第二页之前清空了），`d ∶ e` 那轮仍没抓到，本轮（f ∶ g）也没有，所以这一句的根据是方言册 + 第二页的实测文本，不是首页的见证。
- **没有 `ORDER BY` 时两家都补了一颗，补的是两种东西**：本家补 `ORDER BY (SELECT NULL)`（`DialectBase.cs:461-470`，`PagingRequiresOrdering` 在 `SqlServerDialect.cs:31` 为 true ⇒ 语法要求它在，策略是"不替你排序，只让句子合法"）；对面补 `ORDER BY GetDate()`（`SqlServerQueryBuilder.cs:60` 写死）——那是**每行都不同的表达式**，等于替调用方造了一个不稳定的序。两者都不保证翻页不漏不重，但本家的写法不额外引入跨行变化，对面的会（本文仍未实测并发写下的漏重，见 §6）。
- **计数那句也不同形**：本家是 `SELECT COUNT(*)`，对面是 `SELECT COUNT(1)`（`QueryBuilder.cs:634-641` 的模板，化简成直查表；六趟里那一句原样，一个字节没变）。这一笔只是形状，没有代价差可量。

SqlSugar 不计数那一档也是单条。**首页这一格持平；第二页起两家都是两条，也持平——但两家在第二页上的"合法化排序"不是同一颗，这一格从"持平"变成了"持平且各注不同的东西"。**

### 2.8 读 200 行 × 7 列并物化

FastSql `ToListAsync` **1.32 – 1.73 ms** ∶ SqlSugar `ToList` **1.23 – 1.59 ms**（八趟）。这一格的口被连着改过两次：最早写"对面稳定快约 0.15 ms（10%）"，d ∶ e 那之前的四趟把那句作废（区间重叠 ⇒ 按 §1 第 4 条不排名次）。d ∶ e 那轮把两边的下界一起往下推了一档（1.41 / 1.37 与 1.23 / 1.30），配对读数当时是四副：1.54 对 1.36、1.62 对 1.59、1.41 对 1.23、1.37 对 1.30——**四副全朝同一个方向（对面快 1.9%–12.8%）**。本轮 f ∶ g 又添两副同趟配对：**1.40 对 1.29（对面快 7.9%）与 1.32 对 1.32（一分不差，持平）**，于是那句"四副全朝同一个方向"要降级成 **六副里五副对面快、一副持平、零副本家胜**；本家的下界也被 f ∶ g 那一趟推到 1.32（正好与对面的持平值同数），区间从 1.37–1.73 宽到 1.32–1.73。按 §1 第 4 条它仍然进不了名次档：**两副区间在 1.32–1.59 整个重叠**，而本格八趟跨度是本家 **31%**、对面 **29%**，比那六副配对的差还大。所以这一格现在的口径是：**同一量级、方向没有一副偏向本家、但幅度小于本格的抖动，而且已经出现过一副打平**——"稳定快 10%"那句不许写回来，"完全持平"那句也不许写（六副里没有一副是本家胜，可"对面每副都快"也不再成立）。

### 2.9 一次批量调用里留痕响几次

| 走法 | 读数 |
| --- | --- |
| FastSql L1 装载通道 | `Executed` 响 1 次（这一档不产 SQL 文本，交回的是 `BulkReport`） |
| FastSql L3 多值 | `Executed` 响 2 次（两块） |
| SqlSugar `Insertable(list)` 500 行 | `OnLogExecuting` 响 **1 次**（内含多段 INSERT） |
| SqlSugar `Fastest.BulkCopy` 500 行 | `OnLogExecuting` 响 1 次，文本是 `Begin BulkCopy name:[cmp_sugar] ,count: 500,current time: …` |

SqlSugar 那条"伪 SQL"是设计如此，不是日志坏了：`FastestProvider.cs:548` 在装载前发一句 `Begin {title} name:… ,count: N` 给 `OnLogExecuting`，紧接着 `:545` 把 `Ado.IsEnableLogEvent` **按灭**（先在本机字段 `:544` 存一份旧值），装载结束再在 `:530` 恢复；收尾那一句走 `OnLogExecuted`（`:533`）。所以装载期间真实的驱动侧动作在它的 SQL 日志流里是**看不见**的。而 `:530` 那一次恢复**不在 `finally` 里**——装载一抛，开关就永久留在按灭态，更早那一轮把这一笔量出来了，见 §2.13。FastSql 走的是另一条路：L1 那一档根本不产 SQL，产的是结构化的 `BulkReport`（`src/FastSql.Abstractions/Providers/Bulk.cs:46-54`：`Requested` 与 `Method` 分开记"要哪一层"和"实际走了哪一层"，再加 `RowCount`、`RoundTrips`、`ChunkSize`、`Degraded`、`Reason` 五颗）。§2.1、§2.3 那几行读数里的"7 块 ∶ 每块 315 行"来自与它同源的 `InsertPlan`（`Chunks`/`RowsPerStatement`/`ParameterBudget`），量具把两张单一起打了。

要说清的一件事：`OnLogExecuting` 这一条通道在 SqlSugar 里**同时装 SQL 和装载动作的叙述文本**，接钩子做审计的人会在同一支流里看到两种东西；FastSql 的 `Aop.Executed` 只装真实 SQL，装载另走 `BulkReport`。这是形状之差，不是对错之差——直到 §2.13 那一格，它变成了形状之差**加**一条可用性之差。

裸 `SqlBulkCopy`（自己造 DataTable，不经任何一家）：**19.91 – 31.25 ms**（把造 DataTable 的时间摘出去）／ **22.71 – 33.88 ms**（含造），八趟——f ∶ g 这两趟（25.99 / 28.77 与 29.27 / 23.84）都落在已写的区间里，**这一格八趟与六趟逐字相同**。更早那版本记的是 25.14／25.47 ms，落在同一量级里。四份原文（d ∶ e ∶ f ∶ g）里有**两副倒挂**要说清：d 给的是"只算复制 31.25 / 含造 28.62"，g 给的是"只算复制 28.77 / 含造 23.84"——那两条计时是各自三取最小的**两副独立活**，不是同一次的两个切片，所以"摘掉造表反而更慢"能出现（e、f 两副是正常方向：27.54 对 33.88、25.99 对 29.27）。本文不据此说"造 DataTable 不花钱"，只把这格的用途守住：给 §2.1、§2.3 那几个 30+ ms 提供一个参照。

事务这一档先前只在 §3.3 读码、§6 挂着"没跑"，更早一轮补了。**形制与别处不同**（§1 第 5 条）：计时段是 `begin → 写 → rollback` 整段，所以这一档只跟本档自己比，不跟 §2.1 论高低。`回滚后库里` 那一列是事务真生效的证据，不是装饰。六趟（更早两趟 + d ∶ e + f ∶ g）：

**事务那一层两家都没有可见开销**：FastSql L1 事务内 26.76–32.95 与它事务外的八趟 30.66–123.55 同档（下界 26.76 现在比事务外的下界 30.66 还**低 3.9 ms**，本文不解释，只报读数）；对面装载事务内 23.61–42.62 对它事务外的 28.97–96.03 同档（f ∶ g 那一趟给出的 23.61 同样比事务外下界低 5.4 ms；至此**两家都在这一档出现过"事务内下界比事务外下界低"**，先前只有本家有这一笔）。两边的区间都重叠，名次不报。**先前在这一格写下的两句本轮作废**：① "这一格四趟里没有一个上界被越过"——f ∶ g 越过了两副上界（本家 L3 到 1 412.05、本家 L1 到 32.95）；② "它是全篇目前最'平'的一格（本家 1.10 倍、对面 1.38 倍跨度）"——六趟之后这一格的本家 L1 是 1.23 倍、对面装载是 **1.81 倍**，"最平"那句不再成立，但 §2.1 同一份活在事务外能抖到 4.0 倍、事务内只抖到 1.2–1.8 倍这一对反差还在，本文仍然没有解释它。

然后是更早一轮真正要钉的一颗开关。第五张表 `cmp_chk` 与窄表逐字相同，只多一颗 `CHECK (Amount >= 0)`，往里塞一行 `Amount = -5`。六趟里这五行**逐字相同**：

| 探针 | 结果 |
| --- | --- |
| SqlSugar ∶ 事务外 ∶ `OffIdentity()` 开 | 没报约束错 ∶ **违约行 1 颗进了库**（约束没查） |
| SqlSugar ∶ 事务内 ∶ `OffIdentity()` 关 | **被拒** ∶ `INSERT 语句与 CHECK 约束"CK_cmp_chk_Amount"冲突` ∶ 库里 0 |
| SqlSugar ∶ 事务内 ∶ `OffIdentity()` 开 | 没报约束错 ∶ **违约行 1 颗进了库**（事务内读到 1 颗，回滚后 0） |
| FastSql ∶ 事务外 ∶ L1 默认开关 | **被拒** ∶ 同一条 CHECK 冲突 ∶ 库里 0 |
| FastSql ∶ 事务内 ∶ L1 默认开关 | **被拒** ∶ 同一条 CHECK 冲突 ∶ 库里 0 |

三件事：

- **§3.2 那条"身份列与约束检查二选一"从读码结论升成实测。** 源码上 `SqlServerFastBuilder.cs:52-54` 那一支在事务内且 `OffIdentity` 开着时只传 `KeepIdentity`，于是 `:59` 的 `CheckConstraints` 没了——那五行里的第二、三行就是这一支的两半：不开 `OffIdentity` 时事务里查约束（违约被拒），开了就**不查**（违约行照样进库，还进了事务）。d ∶ e 与 f ∶ g 各两趟给的这五行逐字相同（工作树上那四份原文里各出现一次、一字不差；更早两趟的同一结论只能对到更早那两版文档（提交 `d22ac08` ∶ `4fb6217`）里的表格，原文已被覆盖）。
- **对面事务外根本不查约束**（第一行），这是 `SqlBulkCopy` 的默认语义（`CheckConstraints` 不在默认组合里），不是它的 bug；但它与 `OffIdentity` 叠出来的效果是**"带身份列的装载"在事务里也不查约束**，这跟"事务里就该被约束保护"的直觉相反。
- **本家的事务内外都被拒**：L1 恒传 `CheckConstraints | FireTriggers`，两颗位从驱动自己的枚举读（`SqlServerBulkCopy.cs:152-156` 的理由注释、`:208-217` 的 `Flags`），与是否在事务里无关，也没有一颗口能让你关掉它。这就是先前真库见证里"L1 与逐条等价"的行为来源，更早一轮第一次从约束面上量到，d ∶ e 与 f ∶ g 都复现同一对结果。

一句边界：这一档只用了 `CHECK` 一种约束，外键、唯一索引、默认值、计算列没试；`OffIdentity` 关 + 事务外的组合没测（那一支会因身份列而整体失败，与约束无关）；对面那条老的 `Insertable(...).ExecuteBulkCopy` 路径没测（§3.2 说它完全没有 KeepIdentity）。

### 2.13 走过装载之后，对面的 SQL 留痕还活着吗

这一格是更早那一轮（提交 `d22ac08` 那版）翻车翻出来的：量具第一版把事务段放在中间，跑完之后**后面每一格对面的留痕全是空白**（`OnLogExecuting 响 0 次`、文本 `(无文本)`），一开始看着像对面"装载之后一直不留痕"，其实是一次异常把开关留在了按灭态。于是它被做成一节，每颗探针先把 `IsEnableLogEvent` 拨回 true 再走一步活，然后用一颗普通查询当探针数它响几次——**这样每一步的死活只属于那一步**。六趟（更早两趟 + d ∶ e + f ∶ g）：工作树上那四份原文里这一节连错误文案都逐字相同，更早那两趟的原文已被覆盖、只能对到 `git show d22ac08` 的那张表：

| 走过这一步之后 | `IsEnableLogEvent` | 探针 |
| --- | --- | --- |
| 普通 `Insertable`（10 行） | True | 响 1 次 |
| `Ado.BeginTran + RollbackTran`（不装载） | True | 响 1 次 |
| 普通 `Insertable` **抛异常**（违约行撞 CHECK，不走装载） | True | 响 1 次 |

| `Fastest.BulkCopy` ∶ 事务外 ∶ 违约行（§2.12 已量：约束不查 ⇒ 这一支不抛） | True | 响 1 次 |

**能读出来的只有这一条组合**：让日志停摆的不是装载、不是事务、也不是异常，而是**"事务内的装载抛异常"**这一支——它跳过 `FastestProvider.cs:530` 的恢复（`End` 不在 `finally` 里，调用链 `:497-506` 直排），把开关留在 `Begin`（`:545`）按灭的那一态；而且**它不会自己回来**：紧接着再来一次正常装载也不恢复（上一行倒数第二格），只有手动赋值能救。普通 `Insertable` 抛异常不影响它，纯事务开合也不影响它，两行都在这里验过。

对本家的意义写在两处：① 审计/留痕类调用方如果按"日志流有没有内容"判断连接健康，对面这一支会给出假绿（流断了，但连接照用）；② FastSql 的留痕没有这种全局开关可被掐——`Aop.Executed` 与 `BulkReport` 都是逐次调用交回的对象（§2.9），异常路径上不恢复任何状态。这是形状之差带来的可用性差别，不是对面配错了什么：它的 `IsEnableLogEvent` 本来就是公开可写的开关（`Interface/IAdo.cs:29`）。

一句边界：本轮只测了 `Fastest.BulkCopy` 一条装载口在事务内抛异常的形状（窄表 + `cmp_chk` 违约行），`BulkMerge`/`BulkUpdate` 那两支同样调 `Begin`/`End`、本文**没测**；`isLog` 那颗快照字段在多次嵌套装载下的行为也没测。

- **那些负数是量具的诚实，不是它的 bug**：`执行 -14 次`、`执行 -40 次`、`只跑过一次 -7` 都出现在这一台共享实例逐出计划、清零累计计数的时候（本轮 f 趟有七族、g 趟有八族出现过负数 ∶ f 趟是 `cmp_p2`/`p9`/`p15` 的 `只跑过一次 -7 ∶ -1 ∶ -7`、`cmp_p3`/`p4`/`p5` 的 `-1 ∶ -3 ∶ -1`、本家 L3 的 `-1`；g 趟同样七族之外，两家 ORM 在第一副值上各出 `执行 -14` 与 `执行 -40`）。那两笔在无标签的两族上是**四趟里三趟如此**（d ∶ e ∶ g 三趟原封不动都是 -14 与 -40，只有 f 那趟读成 +7 ∶ +20 的正常增量），所以 `计划 +N` 那一列在这两族上不作数——本家那一族本轮 f 趟读出 `+2 ∶ +0 ∶ +0`、另三趟读出 `+0 ∶ +0 ∶ +0`，同一批本文在三趟里读不出同一种"新增"。它不影响"本族缓存现 N 颗"与那几行全文头（读的是此刻的状态），四趟那一列在这两族上完全一致。
- **"每两副换一批值"那一档（`cmp_p15`）本轮补上了 §2.6 明写没试的中间档，答案是台阶不是梯度**：一副值 2 000 行分七句，rep1 与 rep2 用同一批值、rep3 换新值 ⇒ 墙钟 **550.75 – 572.12 ∶ 29.41 – 33.74 ∶ 417.64 – 424.05 ms**，`计划 +7 ∶ +0 ∶ +6`。也就是 ∶ 复用得上的一副几乎全免（29–34 ms，与"三副同一批值"那族的 19.10–32.13 同档），复用不上的一副照付全价（418–424 ms，与"每副换值"那族的 348.55–623.57 同档），中间**没有**"半新半旧打对折"那一级——因为决定价的是**这套本文里有多少句没见过**，而这七句要么整批新、要么整批旧。折后那颗尾块照例三副共用（13 颗[Adhoc×12 Prepared×1]，那颗 `Prepared` 13 854 字符/执行 3 次）。这一笔把 §2.6 的因果链钉实了：贵的是"本文没见过"，不是"值变了"，两者只是在一趟全换的量具里恰好同向。
- **门限这一格对两家的默认各说一句，两句都只是形状**：本家默认块按 §2.5 那颗旋钮给到每句 315 行（= 1 890 颗参数的参数化形状），而**假如**它走内联，315 行远在门限之上，每副新值就是七句全价——本轮那七族正好给这条曲线补了下半截（170 行起就没有便宜档了）。对面默认那条口按 §3.1 是把每段独立 `INSERT` 全串进**一颗**命令文本，按本族行模板粗算（每行约 57 字符）那一颗就是十万字符量级，远在门限之上 ⇒ §2.6 量到的 3.2–3.8 倍与本轮门限**自洽**。**但这两句都不是见证**：`3g` 里没有"对面默认内联"这一族（它一句里串几段本文没读过、它的颗数也没进取代标签的计划探针），而本家走内联这件事今天不存在（阶梯里没有内联那一级，§3.1）。所以下一轮要证的是把对面那条口接进计划探针，不是再推一次。

**六条口径限制**（读这一格必须先看清）：① `计划 +N` 只对**带本趟字母标签的十三族裸 ADO** 成立；两家 ORM 的表名钉在实体类型上（`[Table("cmp_p6")]` / `[SugarTable("cmp_p7")]`），本轮没法加标签，于是它们的语句本文与上一趟逐字相同，`+N` 只能读成 0——**这一行读不出"新增几颗"，只读"此刻占着几颗"**。② 探针只筛本文里含 `INSERT` 且含表名的语句，`TRUNCATE`、建表、清场都不进计数，但**同名的旧计划如果还没被逐出，会以"本族缓存现 N 颗"的形式混进来**（那两行 ORM 读数因此是"此刻缓存里"的颗数，不是"本轮产生"的颗数——本文按 18+3=21 与 60=3×20 两笔执行次数反查过，它们恰好等于本轮三副值的命令总数，所以这一格的两行可用）。③ 仍未抓 TDS，也没读编译耗时（`sys.dm_exec_query_stats` 不给这一项），"多一颗计划多花多少墙钟"本文只能从同一族的第 1 副与第 2、3 副之间的落差看（270.22–567.82 对 19.10–32.13 ms），拆不出编译、优化与逐出各自的份额。④ **表里"本文 N 字符"那一栏读的是 `LEN(st.text)`，是字符数不是字节数**——上一版把它写成"字节"，本轮全部改称字符；两者在纯 ASCII 上同值，在这一族上不同值（服务端折后文本每行约 126 字符、本家递交的内联文本每行约 57 字符，而落库是 UTF-16）。这一条不只是措辞：上一版那句"门限落在 6 233 与 13 853 之间"拿的是**折后**长度当门限宽度，而门限作用于**递交进去的那一颗**，本轮两侧分开报（第二张表最后一列），才是能用的那道夹。⑤ 每句 200 行那一档的 `计划 +10/+5/+5` 与它第二、三副的便宜墙钟**有一半是量具构造产物**：2 000 行除得尽 200，而每副值整体平移 1 000 行，于是 rep2 的十个块里有五个的本文与 rep1 逐字相同 ⇒ Adhoc 计划被复用。这不是服务端的性质，本文也不把它写进"部分复用"那一档的论证（那一档的见证是 `cmp_p15`，它整副整副地换，没有半块对齐）。⑥ **"递交侧一颗命令多少字符"不是读出来的，是算出来的**：量具没打印它，`3g` 的探针只能看服务端留下的那份。本文按量具的行模板（`(N'客户<i>',7,<i>.25,<i%2>,'2026-10-05 01:02:03.000',N'cmp')` 逐行累加，再加同一颗表头；`cmp_p10f` 与 `cmp_p12f` 表名同为 9 字符，所以 9 205 与 9 219 那一对可比）重算出每一块的长度。这一列比表里其它列**更不可核**——行模板住在 gitignored 的 `sql/obj/sqlsugar-compare/Program.cs` 里，不进版本库，读者要核这一列得自己按同一模板重算；本文因此只用它给门限定位，不用它做任何名次结论。

### 3.3 事务

| 面 | FastSql | SqlSugar |
| --- | --- | --- |
| 嵌套 | `SAVEPOINT` 两条路：方言报驱动支持就交出去，否则自己发文本（`AdoExecutor.cs:309-314`，`fastsql_sp_<n>` 命名）；事务对象带 `IsSavepoint`（`IFastSqlTransaction.cs:21`） | `BeginTran` 里 `if (this.Transaction == null)` 才真开（`AdoProvider.cs:265-270`）⇒ **内层嵌套是静默空转**，而内层 `CommitTran` 会真的提交外层那条（`:308`）。整棵 `Src/Asp.NetCore2` 检索 `SAVEPOINT`/`Savepoint` **命中 0**，保存点这一档不存在 |
| 传播语义 | 显式枚举：`Requires`（并入环境事务）/ `RequiresNew`（挂起、新开、结束后恢复）（`TransactionPropagation.cs:4-12`） | 没有这一档；`SqlSugarClient.BeginTran()` 是"对所有配置的连接各开一条"（`SqlSugarClient.cs:1005-1009` 的 `AllClientEach`）——跨库不是分布式事务，是各管各的 |
| 失败形状 | 异常外抛（回滚后） | `UseTran(Action)` 里 catch ⇒ `RollbackTran()` ⇒ 返回 `DbResult{IsSuccess=false}`，**异常不外抛**，回调可选（`AdoProvider.cs:343-366`） |

| 命名事务 | — | `BeginTran(string transactionName)` 标着 "Only SqlServer"（`AdoProvider.cs:334-335`，实现在 `SqlServerProvider.cs:46-60`）；那是命名事务，**不是保存点** |
| 工作单元 | 会话 + `SaveChanges` 那一族 | `SugarUnitOfWork.cs` 存在，同样没有保存点 |

这一面对 FastSql 最有利，而且有利得很具体：**SqlSugar 的嵌套在源码里就是不安全的**（内层提交 = 外层真提交，内层回滚 = 外层全没了），而 `UseTran` 吞异常这一条会让"以为出事了所以都回滚了"的调用方拿到一个 `IsSuccess=false` 的对象——不看返回值就当无事发生。

事务与装载的交叉更早那一轮补跑了、`d ∶ e` ∶ f ∶ g 各再跑一遍（§2.12，那一格现在六趟）：两家的整批装载放进事务再回滚，`回滚后库里` 都是 0（本家走 `orm.BeginTransaction()` + `tx.Rollback()`，对面走 `Ado.BeginTran()` + `RollbackTran()`），墙钟与事务外同档。这一格只证了"装载真进了事务"，没证嵌套、没证 `RequiresNew`，也没证高并发下的锁形态。

### 3.4 分页

区间重叠的格子一律放进"持平"，这是 §1 第 4 条的规矩。`d ∶ e` 那一轮没有格子从别档搬进持平（持平那六行里只有"装载通道"和"逐条写入"更早就在，那一轮继续重叠），那一轮动的是**名次句本身**：§2.8 那句"对面稳定快约 10%"被区间作废、§2.5 中间两档（每句 100 行与 50 行）的排序因重叠而收回、新增的 §2.12 墙钟与 §2.6 的反超都只钉下界不写"更快"。**本轮（f ∶ g）也没有格子搬档，动的仍是名次句，四处**：§2.5 的"手拼 ADO 比 FastSql 还略慢"、§2.6 的"裸 ADO 参数化换数据反而更快"、§2.8 的"四副配对全朝对面"、§2.12 的"这一格没有一个上界被越过"（§1 第 4 条那"累计七处"里的后四处）。另有一处是加条件而不是挪档：**§2.6 把"内联对面拿不走"这句写死的名次限定成了"只在可复用的数据上"**（见 §5.5），`d ∶ e` 那轮的 §2.14 给它配上机制读数，**本轮又给它加了第二个条件——连"可复用"也看批大小，够小的内联批次由服务端自己折成参数化计划（§2.14 第二条）**。还有一处是本文的因果前提被换了半边：§2.5/§2.6 那两格靠着的那句"参数化 ⇒ 本文恒定"，`d ∶ e` 那轮被 §5.7 打折（客户端那份逐字不变成立，服务端看见的声明表随值的位数走），本轮的 §2.14 把这一笔数成了颗数，**名次同样不动，动的是这一格能主张到哪一层**。

## 5. 被这次对照翻掉、坐实或新钉住的旧说法

### 5.1 打折：规格里那句"SqlSugar 固定行数分块 ⇒ 受参数上限约束"

规格 `docs/fastsql-orm-design.md:1510` 那句话原文是：**"多值语句的参数个数 = 行数 × 列数。500 行 × 30 列 = 15000 参数 —— 在 DM/SQL Server 上直接爆。FreeSql / SqlSugar 都用固定行数分块，换宽表就出事。"** 前一半（我们自己的算法）没错，后一半这次对照下来要拆成两半说：

- **翻掉的是默认那一条。** 分块规则确实是固定行数（`SqlServerInsertBuilder.cs:34-42`），但默认路径把值全部内联（`:61` 走 `FormatValue`），那颗命令文本里**一颗参数都没有**（§2.1 的"参数 0 颗"），2100 这一关它进不去。所以正确陈述是：**SqlSugar 的默认批量不受参数上限约束，受的是"本文长度 + 服务端解析 + 计划缓存"的约束**——这三样里前两项更早那一轮量过（§2.5 那颗手拼对照：内联、每句 315 行、本文比参数化那一档还长，同数据 17.91–37.76 ms 跑完同一批活，比参数化那一档便宜一个数量级），第三项**后面那两轮量出来了，而且它是带条件的**：值一变，那颗手拼对照涨到 251.58–372.94 ms、对面自己的内联涨到 168.32–260.06 ms（§2.6）。所以那句纠正要写成：**默认路径不受参数上限约束，受的是"每趟的本文新不新"约束**；本文长度本身几乎不收钱（同数据下最长的那副反而最快），收钱的是复用不上计划。**本轮这一条还要再补一个条件：连"本文新不新"都取决于批大小，而门限这一轮扫出来了**——服务端自己会把够小的内联本文折成参数化计划：每句 **160 行**那一块（递交侧 9 205 字符 ∶ 960 颗字面量）被折、每句 **170 行**那一块（9 219 字符 ∶ 1 020 颗）没被折，门限夹在这两行之间；每句 50 行那一族 120 句全落在同一颗折后计划上，315 行那一族的主块（递交侧 18 039 字符）没被折、只有它 110 行的尾巴那颗被折（§2.14 第二条与第二张表）。所以"内联付计划的钱"是大批次的性质，不是内联的性质。
- **坐实的是它另外那一条口，而且是从数上坐实的（窄表十二趟、宽表八趟，§2.4）。** `Insertable(list).UseParameter()`（口在 `InsertableProvider.cs:519`）换到参数化实现，那里**确实**按 2100 分块：`ParameterInsertable.cs:129-132` 起点写死 100 行，`:171-187` 拿 `pageSize * count > 2100` 连压三档 50⇒20⇒10。实测两副表各给出一句不超过 2100 的形状（6 列实体 ⇒ 每句 100 行 / 600 颗；30 列 ⇒ 每句 50 行 / 1450 颗，§2.4）。所以"对面也有参数上限意识"这句不算冤枉它，只是**默认路径用不上**，并且它的问法是"撞不撞墙"而不是"多少行划算"。

规格这一轮**不动**（本轮没拿到记账例外），此处只把纠正落在本文，等下一轮再并回规格。【追记·第十四笔（2026-10-06）】那一轮已来 ∶ 规格 §12.3 :1510 就地拆写完（记账例外由用户当面给），本文那句"等下一轮"从今天起读作已兑现；本文这一段原文不动，因为它记的是它自己那一轮的授权边界。

### 5.7 打折：本文那句"参数化 ⇒ 语句本文逐字不变"

§2.6 的整条因果链靠这一句撑着：值内联 ⇒ 每颗新本文要编译；值走参数 ⇒ 本文恒定、只换值。前半句 `d ∶ e` 那轮坐实了（§2.14 第一条）、本轮 f ∶ g 又给它夹出了适用条件（§2.14 第二条：门限之下的本文由服务端自己折掉），后半句被 §2.14 第三条**打折**：

**参数化保证逐字不变的是客户端那份 `CommandText`，不是服务端看见的那一份。** T-SQL 的参数化走 `sp_executesql`，计划身份是"本文 + 那颗声明表"，而声明表里的类型是**带长度的**（`nvarchar(6)`、`decimal(3,2)`）。量具把类型整个交给驱动推断：位数不齐的那一族（三副值同一批、从 1 起，`cmp_p4`）留出来的是 **5 颗计划、3 个桶**（`nvarchar(3)/(5)/(6)` 配 `decimal(3,2)/(5,2)/(6,2)`，§2.14 表格第 5 行），位数齐的那一族（每副值整体平移，`cmp_p3`）留 2 颗（第 4 行）；把 `SqlDbType`/`Size`/`Precision`/`Scale` 钉死之后，同样每副换值的活只剩 **1 个桶**（`nvarchar(512)`/`decimal(18,4)`，第 6 行 `cmp_p5`）。所以准确的说法是：**参数化把"值"从本文里拿走了，但只要类型靠推断，它就把"值的位数"放了回来**——一批 1 位到 6 位宽度不齐的数据，和一批清一色四位的数据，在服务端是两族不同的本文。

这一格在本家身上不是抽象的：`src/FastSql.Providers.SqlServer/SqlServerValues.cs:20-45` 的 `SizeOf` 对字符串取 `Length`、对 `byte[]` 取 `Length`、其余给 0，而 `:24-26` 的注释写着理由——**契约上的 `MaxChars` 会把实参截断，所以本家故意按实参长度报**。那颗 `Size` 随后原样搬进驱动参数对象（`src/FastSql.Core/Execution/AdoExecutor.cs:511-531` 的 `Bind`：`if (parameter.Size > 0) ado.Size = parameter.Size;`）。§2.14 第五条读数里那句"本家逐颗按值的宽度（`@p0 nvarchar(6)`、`@p5 nvarchar(3)`）"就是这条链在缓存里留下的影子。**也就是说：本家的服务端可见本文跟着数据宽度走，这是本家自己写下的策略，不是驱动的意外。**

对面在这一格上是另一种策略，同样从声明表读出来：`cmp_p7` 那一颗的声明是字符串一律 `nvarchar(4000)`、时间给 `datetime`（不是 `datetime2`）——**它把宽度从身份里拿掉了**，所以 2 000 行 × 3 副值 60 句全部落在同一颗计划上（§2.14 第四、五条）。本文对这一笔的表态到此为止：`nvarchar(4000)` 与 `datetime` 会不会带来存储或截断上的差，**到本轮仍没测**（对面的列声明是 `datetime2(3)`，本家用 `datetime2` 的理由在它自己的注释里：`DbType.DateTime` 上线前会把值取整到 1/300 秒，`SqlServerValues.cs:76-78`），只报形状。

四处限制跟着这一句一起记：

1. **本文报不出这笔钱的价**：推断的两族（四趟合起来 1 163.11–3 210.70）与钉死的那一族（1 072.40–2 141.12）墙钟区间整个重叠（§2.14 第三条末），所以"位数不齐 ⇒ 多几颗计划"是真的，"多几颗计划 ⇒ 慢多少"到本轮仍没有读出来。

### 5.8 翻掉：先前写下的"跨趟长尾只出现在 SqlSugar 那两档"

更早那一版在 §2.1 的注里写下过一句判断：那几档读数的长尾（同形状上一趟 53 ms、下一趟 537 ms）是**对面内联与 `BulkCopy` 那两档的性质**，本家的档位跨趟稳。`d ∶ e` 那一轮两笔把它否了：

- **本家 L1 装载通道自己出过长尾**：2000 行 × 7 列那一格 `d ∶ e` 那两趟是 **123.55 与 33.75 ms**（§2.1；本轮 f ∶ g 的 36.62 / 33.71 落在原地，没再越出去），前者是后者 3.7 倍，而这一档当时正落在"长尾只出现在对面那两档"那句的稳的那一边。
- **对面内联那一档那次给的是上界，本轮给的是下界**：宽表 `Insertable(list)` 那一档 `d ∶ e` 两趟是 **150.85 与 36.44 ms**（§2.3 末注：那一档八趟的读数是 37.87 / 38.28 / 38.79 / 39.59 / 36.44 / 150.85 / 35.88 / 37.70）——上界从 77 ms 抬到 151 ms，抬出来的那一趟正是 `d ∶ e`；而下界又被本轮 f ∶ g 压低到 **35.88 ms**，所以"这一档只出长尾"这句在本轮也不成立了。

所以这一句要翻成：**跨趟长尾不认家。**八趟区间给出的跨度是：本家 L1 **4.0×**、本家 L3 1.37×、对面装载 3.3×、对面内联 **14×**（f ∶ g 两趟没有越出这四副区间中的任何一副，所以这四个倍数与上一版逐字相同）。两端都有，量级也不同（内联那一档的 14× 有 §2.14 的机制半边可以归因：每颗新本文一颗计划；本家 L1 那一趟 123.55 本文**给不出归因**，装载通道不发 SQL 文本，计划缓存里根本没有它的槽）。

连带作废的还有本家版的那句"稳"：先前 §6 里"凡本文用'稳定'形容的档位，都是四趟跨度在 21% 以内的那些"这条口径仍然成立，但**更早那一版按它划出来的名单要重划**——`d ∶ e` 那轮 §2.1、§2.3 两格里各有一档从"稳"掉进"抖"。这一格的教训与 §5.1、§5.5 同一族：**本文把"我这一轮没看到它抖"写成过"它不抖"**。本轮新开的那格自己也来了一副：门限扫描里每句 230 行那一档，第三副值两趟是 **413.28 与 803.90 ms**（1.94×，§2.14 第二张表），同一族的主块每句 13 195 字符、形状一颗不差——所以"跨趟长尾不认家"这一句在**本轮新量的格子里当场又中一次**，不是只靠旧格子回填的。
